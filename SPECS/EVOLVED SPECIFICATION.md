# Hypergraph — Unified Project Specification

**Version:** 0.0.1 (implementation baseline)  
**Status:** normative design; not an implementation  
**Implementation:** independent Rust test of concept app, developed in VS Code with Codex and hosted in a GitHub repository  
**Authority:** This is the **single source of truth** for product requirements, technical architecture, interfaces, security, and staged implementation. Other repository files are implementation aids, examples, records, and test evidence—not competing specifications.

## 1. Purpose and scope

Hypergraph is a self-hosted, **single-executable Rust web service** for composing, editing, and publishing interconnected Markdown content. Users can select a sentence, paragraph, section, or document; edit it in place; promote a text selection into an addressable fragment; fork it into an independently editable descendant; or transclude it into other documents. Every fragment retains stable identity, immutable version history, and navigable provenance. Document compositions are directed graphs, not necessarily trees. The editor includes graph search, bidirectional links, a guided table-of-contents and subject-index builder, and scholarly citations retrieved directly from Zotero. The same operations are exposed to suitably authorised AI clients through native Model Context Protocol (MCP) support.

The greater document has a default **`main` branch**: this is the version opened and shown by default. Git-like branch–compare–merge editing is a required workflow for this dissertation app, not a post-v1 extension. Alternative branches support separate lines of work without changing the displayed main version until an explicit integration (§2.1, §2.3). Application branches are independent of the optional GitHub storage mode.

The primary intended use is writing a PhD dissertation: sustained chapter drafting, reusable research notes, traceable revisions, scholarly citations, recoverable backups, and submission-ready exports. This use case guides implementation priorities without tying user content to a particular university template or cloud provider.

### 1.1 Mandatory principles

1. **Content is user-owned and portable.** Ordinary Markdown and documented sidecar metadata are durable source records; the application can export complete, standalone Markdown documents and complete project backups.
2. **Identities outlive locations.** File names, section headings, and display labels never serve as unique persistent node IDs.
3. **Three complementary histories are append-only.** Node history preserves content changes, composition history preserves structural changes, and document snapshot history preserves fully resolved document states (§2.1). Restores append new records. None has an arbitrary revision/snapshot count limit; storage capacity and explicitly documented retention policies apply (§3.2).
4. **Forking differs from reuse.** A fork starts an independent node history with permanent provenance to an exact source revision; transclusion shares the source node history. Live and pinned selections have the semantics in §2.1; snapshots never re-resolve live references.
5. **Graph relations are typed.** Links may form cycles; containment and provenance must obey stricter invariants; transclusion expansion is bounded.
6. **One domain implementation, multiple interfaces.** Browser UI, REST, MCP, and document compiler invoke shared commands, validators, authorisation, and transaction boundaries.
7. **Local first, not local only.** Default binding and Zotero REST integration work on a desktop host; server deployment behind a reverse proxy is explicitly supported.
8. **Security is architectural.** Documents, imported data, API responses, prompts, and clients are untrusted; no feature may bypass domain-level validation.
9. **Accessible by default.** Target WCAG 2.2 AA, keyboard-only workflows, semantic rendering, and screen-reader interoperability.
10. **Independent implementation.** Do not incorporate another application's complete codebase. Established FOSS libraries are permitted under a documented license and provenance process; distinguish dependency use, adapted source code, and conceptual influence.

### 1.2 Initial version and exclusions

This Hypergraph PX test of concept is a **single-human-user dissertation app**, with one human administrator and one separately identified MCP agent principal. The agent is a machine actor, not a second human user. Human and agent retain distinct identities, credentials, permissions and audit attribution; the agent never inherits administrator credentials or unrestricted rights. Concurrent human/agent edits require explicit conflict handling. Additional human accounts, collaborative sharing, live presence and multiple MCP agent users belong to the separate future Hypergraph PX MU app (§1.3), not this version. Keep core actor/history mechanisms reusable without building multi-person administration into this dissertation version.

By `0.1.0`, the primary editor must satisfy the in-place Markdown rendering, caret/selection and five-second idle autosave contract in §2.3; these are core initial-design requirements, not optional polish or post-v1 work. The embedded UI includes conversation with the agent and explicit targeting of sentences, paragraphs, sections, arbitrary valid selections and cursor insertion points (§2.3). User-directed AI drafting, editing, forking, splitting and insertion are in scope. MCP supplies structured access to application operations; it is not itself a model inference or chat service. An agent integration/orchestration adapter must connect UI conversations to a configured model/agent runtime and the shared domain command boundary (§6.1). Unrequested autonomous background editing, federation, arbitrary executable plugins, unrestricted outbound networking and built-in PDF typesetting remain out of scope.

Future implementation includes optional cloud backups (§3.3), an optional GitHub-backed file location (§3.4), and a Pandoc export pipeline with Word/DOCX as its first target (§8.1). These remain planned capabilities. Distinct human/agent identity and in-UI agent interaction remain initial requirements; multi-human collaboration and multiple agent users are deferred to Hypergraph PX MU.

### 1.3 Future separate app — Hypergraph PX MU (Multi-user)

Plan **Hypergraph PX MU** as a separate multi-user application, with its own product/release and deployment decisions, built on shared domain/history/compiler components where practical. This is not an automatic switch of the current dissertation app into a collaborative product. It must preserve the same immutable node, composition and snapshot histories, default-main branch behavior, exact provenance and shared command/authorization boundary. Do not fork divergent implementations of those invariants merely to add collaboration.

- **Multiple human users:** authenticated membership, scoped roles and document/branch access, separately attributed concurrent changes, explicit conflict resolution and revocation. Live coauthoring/concurrency mechanisms require an ADR; typing presence alone does not guarantee simultaneous editing without conflicts.
- **Live typing indicators:** show which authorized human users are typing and the permitted document/section/selection context. Indicators use bounded, ephemeral presence events with expiry/heartbeat, debounce and disconnect handling; they must not persist every keystroke as a content revision or reveal unsent prose. Show stale/offline state honestly and provide accessible textual status.
- **MCP thinking/activity indicators for all users:** show each agent's reported activity to all authorized participants in the relevant collaboration scope. Distinguish queued, processing/generating, running an operation, awaiting approval, idle, cancelled, disconnected and failed states where the runtime provides them. A thinking indicator is visible operational status, not a transcript of private model reasoning. Never invent progress when a client supplies no status; expire stale activity. Publish only permission-scoped agent/task/target metadata, without prompts, secrets or inaccessible content.
- **Multiple MCP users:** support independently authenticated agent principals with separate names, credentials, provider/model profiles, grants, connections and audit trails. Permit concurrent agent sessions and human-directed tasks without conflating identities, conversations, approvals or provider credentials. Agent mutations must satisfy that agent's grants, the initiating human's rights, operator policy and exact target/revision/branch approval. Agents cannot approve their own privileged actions or borrow another agent's authority.
- **Comments:** any authorized human participant can create and reply to anchored comment threads under §2.3; administrator/editor roles can delete individual comments or entire threads. Thread visibility follows document/branch access, not presence or public-content settings.
- **Shared visibility and recovery:** presence/status subscriptions obey current membership and document permissions, including immediate revocation. Reconnect must reconcile current task/commit status without replaying writes. Presence remains ephemeral; actual content revisions, provenance and action outcomes remain durable and attributable. Indicators do not advance document history or alter permissions.

Before implementation, define MU tenancy/membership, identity/credential lifecycle, collaboration transport, ordering/conflict semantics, presence privacy/quotas, accessible UI and deployment in ADRs. Plan an explicit migration/import path that preserves content IDs and all retained histories, reviews access mappings and reprovisions credentials; do not silently upload the dissertation or reuse private tokens. MU planning is recorded here; it does not create a competing specification for the current app.

## 2. Domain and data model

### 2.1 Records

- **Workspace:** configured root directory, stable workspace ID, schema version, storage state, and settings.
- **Node:** immutable UUIDv7 identity (ADR 0004), type (`document`, `section`, `paragraph`, `sentence`, `fragment`, `index`, etc.), creation metadata, optional labels, and a current revision selected by the active branch/read view. Divergent branches may select different revisions of the same node while sharing its one revision DAG; no workspace-global latest revision may silently replace those selections. Identity is independent of path, document membership, display order and payload hashes. A compositional node has a manifest payload; a textual node has a Markdown payload.
- **Working draft:** mutable, durable, actor- and branch-scoped editing state anchored to exact committed node/manifest revisions and snapshot. Autosave replaces this working state without creating revisions, snapshots, provenance records or branch-head transitions. Draft generations and recovery receipts are concurrency metadata, not revision history. Committed history remains immutable; drafts never masquerade as committed snapshots.
- **Revision:** immutable logical revision ID, owning node ID, zero or more parent revision IDs of that same node, actor, time, transaction ID, payload object digest and provenance references. Every MCP/agent-authored change also retains its model attribution (§2.1), directly or through an immutable transaction attribution reference. Payloads may be deduplicated without collapsing distinct revision events or node identities. Revision-parent relationships form a DAG; cross-identity derivation uses provenance edges, not revision parents.
- **Document manifest:** a revisioned ordered structure of inclusion entries, document-local Markdown, labels and presentation metadata. Each inclusion has a stable inclusion ID, target node ID, selection rule and optional source anchor; repeated inclusions of one node have distinct inclusion IDs. Reordering retains inclusion identity; removal is a new manifest state, not deletion of the target. Nested composition-capable nodes use the same rules.
- **Document branch:** stable branch identity and name, greater-document/root identity, creation/base provenance, current exact root manifest revision and complete snapshot ID, with append-only branch-head transitions. Create `main` with the first greater-document state; default open/read/preview resolves `main` unless the user explicitly selects another branch or historical snapshot. Branch heads select coherent document states, not Markdown filenames or storage-provider branches. A branch initially shares immutable source revisions/snapshot dependencies; do not duplicate node histories. Editing another branch cannot silently advance main. Branch/read-view mechanisms require the ADR in §11 before composition implementation.
- **Document snapshot:** an immutable snapshot ID, root document ID and exact manifest revision, capture transaction/read-view marker, a finite resolution closure, integrity digest, and reconstruction profile. The closure records each reachable included node/manifest revision and the exact target selected for each inclusion slot (binding-context ID plus owning revision ID and inclusion ID), including nested transclusions, original selection rules and repeated uses. The same node may appear at different pinned revisions, and the same manifest revision may appear under different historical closure pins. Distinct binding contexts preserve each subtree's selections; neither a node-ID-only map nor a revision-only map is sufficient. Identical payloads/closures may share storage without losing inclusion occurrences. Include document-local prose through its manifest payload, and pin required local assets, citation metadata, and compiler/extension profile for deterministic materialisation. Persist capture purpose, completion/diagnostic status and fixed diagnostics; a failed or incomplete capture must never be presented as a complete snapshot.
- **Edge/provenance record:** typed identities and exact source/result revisions, transaction, optional range/anchor, inclusion ID, order and annotation. Durable records retain the historical relations of each owning revision; current and reverse indexes are derived views. Multi-source derivations preserve an ordered source list with contributing ranges and output mapping.
- **Logical reasoning link:** independently identifiable, revisioned annotation with a stable operator ID and operator-definition version, ordered node/expression operands, original live/pinned target rules, optional explanation and logic-system/context parameters, actor/model attribution and transaction linkage. Any content node can participate regardless of type or document location; repeated operands and self-links are legitimate annotations. Preserve distinct occurrences and exact selected revisions in captured historical reasoning views. A logical assertion is not a containment/transclusion edge, proof, content identity equivalence or edit authorization.
- **Logic operator definition:** versioned namespaced identifier, human label, symbol/aliases, logical family/system, operand count/roles, required context and documented intended meaning. Preserve the exact definition version with existing links; adding or renaming a display label cannot reinterpret older assertions. Include an extensible catalogue rather than claim a finite exhaustive list of all philosophical logics. Workspace-defined labelled operators are data, never executable plugins.
- **Selection anchor:** source node/revision, Unicode-safe source range and text-context checksum, plus containing document/manifest/inclusion context where applicable. For document-local Markdown, identify the exact local part/payload and owning manifest revision; a rendered position or heading label alone is insufficient. The editor maps its transient buffer version and visible selection to these durable source anchors at commit/action submission. Historical anchors always identify their original immutable bytes; rebasing a selection against a current revision is explicit and conflicts if ambiguous.
- **Comment thread (future):** stable thread identity, document/branch and inclusion context, exact sentence/paragraph/section selection anchor, author, timestamps and open/closed status; ordered, individually identifiable comments/replies retain their authors and reply relationships. Keep comment lifecycle and visibility separate from prose, agent conversations and the three content histories. Deletion records a permission-checked tombstone; it never rewrites document revisions or snapshots.
- **Citation identity:** Zotero provider, API mode, endpoint instance, library kind and ID, item key; workspace citekeys are separate aliases.
- **Index view:** saved query/filter, selected node IDs, ordering, hierarchy, annotation labels, and revision. When embedded, its materialised ordering and selected revisions belong to the snapshot closure; historical reconstruction must not rerun a current query.
- **Transaction:** immutable commit identity and durable change set linking revisions, composition changes, provenance, head transitions, snapshots and audit outcome. Its commit is the visibility boundary across all interfaces (§3.2).
- **Principal and actor/action grant:** stable human or agent identity, account status, role and scoped permissions, expiry/revocation, and audit trail. Initially create one administrator and one non-admin MCP agent principal. Persist the authenticated execution actor on every revision/transaction; record the initiating human, agent identity, request/action grant and conversation/turn linkage separately when delegated. Never attribute agent-generated changes solely to the administrator. Secrets are separate from content.
- **Model attribution:** mandatory identifying information for every MCP/agent edit: provider identity, exact requested model identifier, provider-reported model identifier/version or snapshot when available, agent actor, originating request/turn/proposal and transaction linkage, and attribution source/trust classification. Application-runtime observations and external-client declarations are distinguished explicitly; do not present an unverified client claim as provider-verified identity. Model identifiers must be nonempty, bounded and retained immutably with the resulting content/manifest revisions and transaction/audit record. Capture available provider request IDs without secrets. When exact internal model version is not exposed, record that limitation rather than inventing a version; the configured/requested model identity is still required. Attribution identifies the model responsible for the accepted proposal, even if configuration switches before approval/commit. A restore records the model performing the restore while preserving the original source revision's attribution.
- **Conversation and agent action:** permission-scoped conversation/turn IDs, participating principals, retained user prompts and agent replies in turn order, explicit target descriptor, proposal and execution status, action grant, and resulting transaction IDs. Chat is not authoritative document content; an assistant message or displayed preview is never evidence of a committed edit. Recover interrupted actions by transaction identity rather than resubmitting them blindly.
- **Editing target:** discriminated node/range/cursor target anchored to exact source node/revision and relevant document/manifest/inclusion context, branch identity and expected branch head. Range targets use the selection anchor above; a cursor is a zero-width Unicode-safe boundary with neighbouring-text checksum and explicit insertion affinity. Section or multi-node targets carry all affected identities, revision preconditions and ordered ranges. A shared node's inclusion context distinguishes changing the original from forking or changing only one use.

Autosaved working drafts are outside these histories. Their replacement does not constitute a committed edit; explicit publication creates immutable history through the usual transaction boundary.

The three histories are distinct but transactionally connected:

| History | Append-only records | What advances it |
|---|---|---|
| **Node history** | A node's revisions and their same-identity parent DAG | Explicitly committed content/metadata edits, conflict-resolved revision merges, and content restores; first revisions have no parent, subsequent revisions retain same-identity parent(s) |
| **Composition history** | A document/compositional node's manifest revisions and structural change records | Extract, split, insert, remove, move/reorder, replace with fork, merge structures, transclude, change a live/pinned rule, or change a revision/closure pin |
| **Document snapshot history** | Explicitly captured immutable root-and-closure records | Initial document creation and each committed manifest change capture a state atomically; explicit captures and exports can capture later live-dependent states without changing the manifest |

Composition history is the structural node's manifest-revision history, not a competing second authoritative manifest log. Committed changes to document-local prose also advance that manifest, labelled as textual changes with no fabricated structural delta. Committing an edit to a referenced paragraph advances that paragraph's node history without advancing each containing manifest or copying paragraph revisions into each document. Existing snapshots remain unchanged. A document can therefore have multiple snapshots for the same manifest revision with different resolved live dependencies. The UI must not imply that an uncaptured intermediate live view was recorded; request/work budgets and pagination limit operations, never the total history count.

**Reference selection:** `live` selects the target's current committed revision in one consistent capture read view; `pinned` names an exact revision belonging to that target identity. Pinning a compositional node's revision alone does not freeze live references inside it. A closure pin additionally identifies a retained snapshot resolution closure, or equivalent fully resolved immutable bindings, for the selected subtree. Snapshot reconstruction always uses its recorded closure and ignores subsequent head changes. For unbound live uses of the same target in one read view, resolve the same head; explicit revision/closure pins may intentionally select other historical revisions. A closure-pinned subtree retains its own resolution context even when the same manifest revision is reused elsewhere with a different closure. References are not copies of the source node's history.

### 2.2 Relationship semantics

| Edge | Meaning | Cycles |
|---|---|---|
| `contains` | Ordered structural inclusion with an owning manifest revision and inclusion ID | Prohibited in each committed containment graph |
| `links_to` | Navigational hyperlink, including descendant-to-ancestor links | Permitted; never implicitly expanded |
| `transcludes` | Shared content selected by the reference rules in §2.1 | Stored cycles permitted; expansion detects/bounds cycles (§2.5) |
| `forked_from` | New identity derives from an exact source node/revision and optional range | Prohibited in derivation ancestry |
| `extracted_from` / `split_from` | New fragment identity derives from exact source revisions/ranges and original composition context | Prohibited in derivation ancestry |
| `merged_from` | New content/structure derives from multiple exact source revisions with contribution mappings | Prohibited in derivation ancestry |
| `restored_from` | A new restore result identifies the exact earlier revision or snapshot whose state it copies | DAG over immutable derivation events |
| `revises` | Same-identity revision-parent relationship, including a resolved multi-parent revision merge | DAG only |
| `cites` | Content cites a bibliographic record | Permitted |
| `annotates` | Annotation targets node or immutable revision/range | Permitted |
| `logical_relation` | Versioned labelled reasoning expression over ordered node/expression operands, with the operator semantics in §2.4 | Permitted as annotations; never implicitly evaluated or expanded |
| `indexes` | Saved index refers to content | Permitted; no implicit recursive materialisation |

A node can appear repeatedly and in many compositions. Provenance relates immutable result revisions to exact source revisions; subsequent independent edits extend the result's revision history without rewriting that origin. Validate ancestry against revision-level derivation events so legitimate future content exchange between identities is not confused with a cycle between historical events. Fork/extraction/split origins are first-class durable records; incoming “forked to”, “extracted to”, “split to” and merge contributions are navigable in both directions even after source removal from a document or index rebuilding. Permission checks still apply to both directions (§7.1).

A missing target is reported as dangling, never silently redirected to a new head or unrelated identity. Historical edges remain available from their owning revisions; rebuilding a current edge index must not erase them.

### 2.3 Editing behaviour

- **Planned four-column writing workspace:** on desktop/wide screens, arrange the primary workspace from left to right as (1) a hierarchical contents/index navigator showing chapters, sections and subsections, (2) the primary in-place Markdown editor, (3) a narrow document minimap, and (4) a right-side panel with exactly two primary tabs: **Agent** and **Comments**. Give the editor the main writing area. The contents navigator uses stable document/inclusion/source anchors and current displayed branch/draft state; headings are labels, never persistent identities. Selecting an entry reveals its corresponding source location without changing text or branch history. Panels may be resized or collapsed with keyboard-accessible controls; preserve viewing preferences without changing document content. Desktop is the current implementation target. Mobile/narrow-screen responsive panels and drawers are deferred to the future mobile plan (§8.2); they do not block the current desktop implementation or the `0.1.0` editor gate. Preserve desktop keyboard, screen-reader and zoom accessibility.
- **Planned document minimap:** provide a miniature source/code-style overview beside the editor, like the owner-supplied editor screenshots, including a marker for the currently visible range. Clicking the minimap or dragging its viewport marker navigates the same document; provide keyboard-accessible equivalents and a show/hide control. Synchronize the overview with the displayed source, scrolling, edits, wrapping/reflow, active branch and recovered working draft. Use the composed source ownership map so repeated inclusions and document-local prose navigate to the correct occurrence. Minimap navigation is presentation only: it must not edit text, commit drafts, advance histories, change the frozen target of an existing agent request or disclose another branch/inaccessible content. Keep rendering work bounded on long dissertations. The minimap supplements accessible document/heading navigation and must not duplicate the whole source in screen-reader output.
- **Agent/Comments tabs:** the fourth column contains the existing conversation/action UI in Agent and anchored discussion under the comment rules below in Comments. Use semantic, keyboard-operable tabs with announced selected state. Switching tabs or collapsing the panel preserves editor selection/caret, unsent prompts, retained threads, agent request identities/proposals/approval state and live work; it never grants approval, cancels a request, closes a thread or deletes data. Selecting a comment reveals/highlights its exact source anchor and vice versa. Closed-thread navigation and comment show/hide controls live within this same panel; no separate fifth desktop column is implied. Comment permissions, tombstones and original/outdated-anchor behavior remain unchanged.
- **Primary in-place Markdown editor — required by `0.1.0`:** the document the user sees, navigates and edits is one editable rendering of the Markdown source with its syntax retained visibly. For example, `# Heading` must still display the literal `# Heading`, styled and exposed accessibly as a heading. Retain visible Markdown delimiters, indentation and source text while applying the corresponding visual structure; do not hide syntax merely because the caret leaves a block. Mouse clicks position the caret in that same surface, and typing, deletion, paste and replacement occur there. All editable document content, including the first heading and document-local prose, participates. A separate raw textarea plus read-only preview, or a rich-text view that removes Markdown markers, does not satisfy this contract. Optional diagnostic/source views may supplement the editor but cannot be required for ordinary writing. Every independently addressable sentence, paragraph, section or fragment retains its own node history; unidentified inline text remains part of its owning revision until extraction.
- **Caret, movement and selection:** show a visible insertion caret at the exact typing position. Support standard platform editing/navigation combinations for characters, words and line start/end, plus documented keyboard commands for sentence, paragraph and section start/end. Where a platform has no standard sentence/section shortcut, provide a discoverable default and accessible command equivalent without overriding established OS/browser shortcuts. Shift with arrows and the corresponding movement combinations extends the selection from its anchor, including by sentence, paragraph and section; mouse dragging and keyboard selection operate on the same source ranges. Define line movement clearly for visually wrapped versus logical lines, and retain the caret/selection through styling updates, reflow, autosave and acknowledgements. Support platform-standard undo/redo; undo changes the working draft; undo of a committed edit creates a new revision only when explicitly committed, never by rewriting history.
- **Selection defines operation scope:** the visible selection is the default target and exact boundary for agent actions, branching from a selection, forking, extraction, splitting and other selection-based commands. The visible caret is the target for insertion. Opening chat or an action menu must preserve the editor selection; ordinary operation must not require separately recapturing focus or manually copying text to another field. Cross-node/section selections carry ordered per-source anchors and inclusion contexts. Document branches still record complete coherent document snapshots (§2.1); a selection-scoped branch operation limits the selected contribution/edits and preserves unselected content, rather than granting an implicit whole-document replacement or conflating document branching with a new node identity. If an operation needs addressable fragments, create them atomically under the existing extraction/split provenance rules. An empty selection does not authorize replacing a whole node. Any required syntax-boundary expansion must be visibly reflected and accepted before the action; never silently substitute a larger target.
- **Five-second idle autosave:** after more than five seconds without a text-changing input, durably save the mutable working draft and its corresponding current Markdown files (§3.1), without creating a node revision, manifest revision, snapshot or branch-head transition. Restart the timer on text changes, including paste, deletion and completed IME input; selection-only navigation does not restart it. Do not save unfinished IME composition. Ordinary typing needs no Save button. Provide a separate explicit **Commit revision** action to publish the draft through the common authorized atomic history transaction; accepted agent edits and structural commands remain explicit, attributed history operations. Show draft saved/uncommitted separately from committed, saving, conflict and error states. Bind draft acknowledgements to buffer generations and exact committed bases; newer typing survives older acknowledgements. Use atomic confined writes, restart recovery and optimistic concurrency; stale drafts never overwrite a changed branch or another actor's draft. Draft persistence and recovery metadata must not accumulate as disguised revision history. Before an action requiring committed anchors, explicitly include publication of pending draft bytes in the reviewed action or block with a clear explanation; merely opening chat, capturing focus or autosaving must never commit implicitly. Navigation/close preserves or explicitly warns about pending draft work. Historical reconstruction uses committed immutable objects only, never mutable working files.
- Selections support sentence, paragraph, heading/section and arbitrary in-block ranges. Cross-block selections are explicit multi-node operations. Preserve Markdown formatting, citation syntax, Unicode and source mapping; never split syntactic constructs blindly. Preview affected source uses, resulting identities, structure and provenance before committing structural operations.
- **Branch-aware authoring:** visibly show the active branch and default to `main`. Branch creation starts from an exact recorded source snapshot and retains its provenance. Saving content or structure in a branch advances that branch to a newly captured coherent state; content-only saves may capture a new snapshot with the same root manifest revision, preserving the distinction between node and composition history. Do not advance every referencing document/branch or copy shared node revisions. The default main view uses its selected recorded closure rather than resolving unrelated newer source heads. Live references still resolve according to §2.1 when explicitly capturing the active branch; reconstruction never follows later heads. Preview dependency changes before integrating them. Switching branch never commits, merges or discards pending work implicitly. Merge into main is an explicit expected-head-checked operation with conflict preview and preserved source histories, manifest history and required snapshot; do not silently merge or rewrite branch history. Global shared-source edits remain separate explicit actions with impact warnings.
- **Compare and merge branches:** compare two exact snapshots, a working branch against `main`, or either side against their recorded common base. Return identity-aware structural changes (insert/remove/move, fork/replace, inclusion-rule or pin changes) separately from Unicode-safe prose diffs; reordering a stable inclusion is a move rather than an invented deletion/new identity. Include nested dependency changes even when the root manifest is unchanged, and distinguish repeated occurrences and their binding contexts. Offer accessible inline and side-by-side comparisons without modifying either state. Three-way merge uses retained ancestry and exact base/source/target snapshots; automatically combine only demonstrably independent changes. Surface overlapping prose edits, edit-versus-remove, incompatible reorder, conflicting reference rules and divergent nested bindings for explicit resolution. If a unique merge base is unavailable, require an explicit reviewed base or report the ambiguity; never guess from timestamps. Allow selected changes to be integrated, preserving unselected work on its source branch. A merge preview binds its base, both heads, selected changes, resolutions and resulting dependency closure; recheck these at commit and reject stale previews atomically. Append a merge record linking both source states and the actual selected contributions, appropriate same-identity parent revisions, manifest changes, model/actor attribution and a complete resulting snapshot; never claim unselected changes were integrated. Advance only the target branch. Repeated integration must not duplicate previously accepted changes, and recovery must reproduce the same merge and retained histories. Branch creation, comparisons and merges work locally without Git or GitHub.
- **Agent conversation and focus:** derive a new turn’s target from the primary editor’s preserved visible selection/caret under the rules above, freezing its exact committed anchors at submission. A diagnostic focus-preview control is supplementary, not a required ordinary targeting step. Provide an embedded conversation pane where the administrator can instruct the agent and attach the current sentence, paragraph, section or arbitrary valid selection. Display and highlight the attached target, document/inclusion context, source revision and intended operation (edit, fork, split, extract, merge or insert). Include active branch identity and expected branch head in targets, proposals and approvals. Sending a turn freezes its target; moving focus, navigating documents or clicking elsewhere must not silently retarget an outstanding action. Offer explicit retargeting as a new request. Resolve sentence/section boundaries through Unicode-aware Markdown source maps, not rendered character offsets or English punctuation alone. Only send permitted context; expanding beyond the selection requires a visible, permission-scoped context policy.
- **Conversation visibility:** display the user's prompts and the agent's replies as ordered, clearly attributed exchanges associated with their targets and resulting actions. Each prompt has an individual expand/collapse control for that prompt and its associated replies. Provide a universal **Expand all / Collapse all** control for the conversation exchanges in the interface. A global action sets all exchanges to the chosen state and sets the default for newly arriving exchanges; subsequent individual toggles override only that exchange until the next global action. Initially show exchanges expanded. Collapsed exchanges retain a compact prompt summary and status so they can be found and reopened. Hiding an exchange only changes presentation: it never deletes prompts/replies, cancels execution, changes agent context or grants approval. Keep action status and any required approval accessible while conversation text is collapsed. Visibility preferences belong to the viewing user and must not change another participant's view.
- **Cursor-directed agent insertion:** allow the user to place a cursor at any valid text boundary, including beginning/end and an empty editable block, and request agent text there. Map the rendered caret to an exact Markdown source anchor. Insertion appends a revision of the owning text node; insertion of structural blocks revises the containing manifest and captures its required snapshot atomically. Never guess a different position, replace surrounding text, or split an invalid Unicode/Markdown boundary silently. An insertion affecting shared source shows its impact and offers the existing original/fork-here choice. Historical views require an explicit restore/fork/retarget action before editing.
- **Agent proposals and execution:** show proposed text/structural diffs, source/shared-use impact, new identities and provenance before approval. The default is preview then human approval, with any explicit delegated action grant limited to the operation, exact targets, expected revisions, expiry and requesting principal. Free-form document text, model output and chat messages do not create grants. Reject stale or ambiguous anchors and concurrent edits with a conflict and refreshed preview; do not silently rebase, overwrite, move the insertion point or repeat an uncertain commit. Support cancellation and show whether an action is proposed, running, committed, failed, cancelled or requires reconciliation; cancellation after commit preserves the revision and offers an append-only restore.
- **Edit:** retain node identity and append a revision after an `expected_revision` check. Editing shared content advances its single history; live uses can display the new revision, while pins and historical snapshots remain unchanged. Do not create duplicate revisions in referencing documents merely to reflect that change.
- **Promote/extract:** create an addressable node whose first revision records `extracted_from` with the exact source revision/range and original manifest/inclusion context. If replacing the selection in its document, append the changed source revision (if needed) and manifest revision in the same transaction. Moving the remaining source text or references must retain an output-to-source mapping; original prose is not replaced without a corresponding committed history record. Preserve earlier source revisions, source-document states and ancestry; never relabel the fragment as if it had existed independently before extraction. Merely moving an already-addressable node retains its identity/history.
- **Split:** retain the original identity and earlier revisions; create new identities for the selected parts, each with `split_from` provenance and exact source/output ranges. Replace the affected inclusion(s) in a new manifest revision; retain the original source by default. Tombstoning it requires a separately authorized, previewed shared-source action; replacing one use must not break other live uses. Never transfer its old revisions destructively to the children. Splitting a document follows the same rule for new document identities, source manifest and partitioned inclusion context.
- **Fork:** create a new identity and first revision with `forked_from` to the exact source revision/range, starting an independent revision history. A “fork here” action also replaces only the selected inclusion in a new manifest revision; other uses continue referencing the source. Preserve permanent bidirectional lineage and earlier document states. Forking an entire document explicitly records whether its included nodes remain shared or are individually forked; do not imply that a shallow fork deep-copies node histories.
- **Insert/remove/rearrange:** append a manifest revision recording inclusion IDs, before/after order, targets and selection rules. Removal detaches a use; it does not delete the node or history. Moving content between documents atomically revises both manifests with preconditions for each; cross-document provenance and prior snapshots remain intact.
- **Merge:** distinguish (a) composing existing nodes/documents into a new or revised manifest, preserving their identities and independent histories; (b) combining prose into a new node with `merged_from` records for every source revision/range; and (c) resolving divergent revisions of one identity with a new multi-parent revision. Preview and resolve conflicts explicitly; never erase source histories, concatenate unrelated histories under one identity or rewrite parents to fake common ancestry. Document merges preserve source manifests and their snapshots.
- **Transclude/pin:** use §2.1 selection rules. Before editing shared source, show its uses and offer **Edit original**, **Fork here**, or **Pin revision**; expose a closure pin when nested live dependencies would otherwise remain movable. Changing a selection or pin is a manifest revision, not a source-node edit.
- **Anchored comments (future):** the human author in PX, and any human user with access and permission to comment in PX MU, can attach a comment to a sentence, paragraph or section, reply within its thread, or mark a thread as dealt with to close it. Closed threads leave the active discussion view and remain available through an explicit closed-thread view. Show comments in the Comments tab of the fourth, right-side workspace column; selecting or focusing a comment highlights its exact target, and selecting the target identifies its thread, with an accessible non-colour-only association. Provide show/hide controls for the Comments view/right-side panel; hiding comments is a per-user presentation preference and neither resolves nor deletes them. The future mobile plan (§8.2) will provide a narrow-screen tabbed panel/drawer preserving the target association. Store exact revision anchors and inclusion context using §2.1: edits, rearrangements, splits, forks and transclusions must not silently attach a comment to different text or copy it to every use. Preserve navigation to the original target; identify outdated or ambiguous anchors explicitly and require confirmation for retargeting. Administrators and users with editor rights in the relevant scope can delete an individual comment or an entire thread, including its replies; ordinary commenting permission does not grant deletion rights. Individual deletion retains other replies and their threading via a placeholder. Deletion follows tombstone semantics, distinct from closure and visibility, and does not promise irreversible erasure. All comment create/reply/close/delete commands and reads use shared authorization, expected thread state, atomic persistence and audit; treat comment text as untrusted. Comments do not change compiled prose or content snapshots unless explicitly included in an annotation export.
- **Capture snapshot:** record one consistent resolved document state without mutating source nodes or implicitly changing inclusion rules. Each committed initial/changed manifest also captures its resulting state (§2.1); conflict/failure aborts the whole transaction. Explicit captures need write permission because they persist history; read-only previews return a temporary resolved view without a durable snapshot ID.
- **Restore:** a node restore appends a new revision copying the selected old payload, with current head as parent and an exact `restored_from` audit/provenance reference; it never rewinds the head or overwrites earlier records. A composition restore appends a manifest revision with the chosen historical structure; copying live rules does not promise historical text. An exact snapshot restore appends a new manifest revision bound to that snapshot's complete resolution closure and captures a new snapshot; by default it does not edit or rewind shared source nodes. Restoring source content globally requires a separate previewed multi-node operation, write grants and current-head preconditions for every affected identity.
- **Delete:** tombstone; preserve retained histories, inclusions and snapshot dependencies. Irreversible purge is outside v1; any later policy must meet §3.2 and separate impact confirmation.
- Every write through UI, REST or MCP invokes the same validated domain command and atomic transaction. Validate all expected node/manifest heads and source anchors, then commit changed revisions, structural deltas, provenance, required snapshots and audit together. Return actionable conflicts without partial writes or automatic retries of non-idempotent operations. MCP/agent changes require model attribution; approving an agent proposal must not relabel it as solely human-authored or attach a newly selected model to an older proposal.

### 2.4 Composition, graph navigation, and indexing

A composed document can interleave its own prose, sections, fragments, links, transclusions and forks from independently versioned sources. Its manifest history preserves all structural actions in §2.3 independently of the included nodes' content revisions. Compositions do not flatten or copy constituent histories into a monolithic document revision. Scholarly compositions default to pinned selections with closure pins for nested live dependencies; live reuse is opt-in and visible.

The compiler has two explicit inputs: a current document/manifest resolved under a consistent read view, or a recorded snapshot ID. Capture resolves the whole reachable inclusion graph, including nested manifest revisions and repeated/differently pinned uses. Persist the closure before calling a build a recorded state. Reconstructing a snapshot must never consult current node heads, current saved-query results, current directory names or Zotero responses. Deterministic materialisation returns the same Markdown bytes, ordered source/provenance mapping and fixed diagnostics under the recorded reconstruction profile; required assets/bibliography are pinned. Later compiler versions must retain compatible reconstruction or provide an explicit versioned migration preserving original objects and reconstruction capability. DOCX/package byte-level limits remain as specified in §8.1.

A historical manifest alone is a structural version; if it contains live references without a recorded closure, reconstruction of its historical text cannot be guaranteed and must be reported as unavailable rather than guessed. Export and explicitly saved build states retain a durable snapshot; a read-only preview can use an ephemeral resolution closure and must be labelled uncaptured.

Graph search covers titles, IDs, text, aliases, tags, citations, backlinks, derivations, ancestors and revisions, with history/snapshot scope and pagination. `contained_in`, `descendants_of`, `forks_of` and `cited_by` obey query budgets and current actor permissions. Renames/moves do not change identities. History views offer separate content, composition and snapshot timelines, plus a transaction-linked combined view. Show structural versus textual differences, source/result revision IDs, extraction/split/merge origins, live/pinned/closure-pin state, capture completeness and the impact of restore; retained historical states are read-only until an explicit restore creates new records.

**Logical reasoning connections:** allow the author to connect any sentence, paragraph, section, document or other node to any other with explicit operator labels. The owner selected **labelled reasoning links first**; formal proof checking/truth evaluation is a later, separately specified capability. Initial catalogue includes AND (∧), inclusive OR (∨), binary XOR (⊕), NOT (¬), NAND, NOR, material implication (→), biconditional/IFF (↔, also binary XNOR), and their documented direction/operand roles; modal necessity/possibility, epistemic knowledge/doxastic belief, deontic obligation/permission/prohibition, temporal past/future operators, conditional/counterfactual labels, universal/existential/unique-existence quantifiers, and distinct entailment/derivability labels. These families have different semantics: never conflate material implication with semantic entailment, knowledge with belief, or material with counterfactual conditionals. Unary operators apply to one operand, binary operators to two; grouping and multi-premise expressions must retain explicit structure and order. Quantifiers require a future expression/binding model before formal evaluation; a quantified label on prose alone is not a validated quantified formula. Predicate identity/equality annotations must not merge content-node identities.

Offer an accessible operator picker with names, symbols, explanations, operand roles and search/filter by family; create/inspect/edit/remove logical links from node selections and graph/table views, with reverse navigation. Display the distinction between author assertion, model suggestion and any separately implemented verified result. Allow custom namespaced labels and explicitly identified nonclassical systems (such as intuitionistic, relevant or paraconsistent logic) without silently applying classical truth tables or inference rules. There is no claim that the initial catalogue exhausts philosophical logic. Logical cycles, including self-links, are legal and never trigger recursive document expansion; separately bound nested-expression traversal. Permission-check every operand and redact/deny inaccessible targets. Agent-created links require normal proposal/approval, grants, expected revisions and immutable model attribution.

Logical-link and operator-definition edits append history and commit through the same journal/authorization boundary; branch isolation, merge comparisons, provenance, snapshot capture, recovery and rebuild must preserve exact historical assertions and definitions. Content edits do not rewrite prior logical labels or count as proof; live target changes are visible and snapshots retain exact selected targets. Source/standalone exports may include reasoning sidecars; reasoning annotations do not insert prose or change document compilation unless explicitly selected for export. REST/MCP expose the same versioned catalogue, scoped query/preview and authorized link commands. Implement label-only data-model primitives first, durable graph/history and common commands next, then browser/MCP workflow under stage 5; formal evaluation needs its own reviewed logic-system/grammar/semantics ADR.

The **contents builder** and **subject-index builder** support search/browse, include/exclude, drag or accessible keyboard reordering, labels, saved filters, nesting, link-only versus embed, preview and durable versioned manifests. Index labels can target multiple arbitrary passages. Their structural changes follow the same composition-history rules; captured results are frozen in the snapshot closure, not silently rerun during reconstruction. Ancestor links are valid and never implicitly recursively materialised.

### 2.5 Expansion safeguards

Snapshot capture and rendering have different traversal duties. Capture records a finite graph of immutable revision-and-binding-context vertices and resolved inclusion slots; visited-vertex tracking may avoid resolving the same vertex twice while retaining every edge and inclusion ID. Rendering tracks the **active traversal path** of node/revision/binding-context inclusions rather than a global visited set, so repeated legitimate use renders repeatedly while cyclic transclusion terminates with a diagnostic/linked placeholder. Containment and revision/derivation ancestry obey §2.2 acyclicity checks at mutation time; hyperlink cycles remain valid and unexpanded.

Both operations enforce depth, resolved/expanded-node count, output bytes, wall-clock/work budget and cancellation. Exceeding a capture budget cannot silently omit a dependency or produce a supposedly complete snapshot. A capture with unresolved targets or cyclic/truncated expansion is explicitly diagnostic, retaining resolved selections and stable diagnostic locations/profile; it must not be accepted as a complete scholarly export. Complete snapshots include every required dependency. Historical rendering under a smaller runtime budget fails explicitly rather than substituting newer revisions or claiming an exact reconstruction. Results report completion, unresolved targets, live dependency changes, source revision IDs and whether a view was durably recorded.

## 3. Filesystem, persistence, and recovery

### 3.1 Single executable and workspace

Build one distributable native binary containing server code, embedded frontend assets, REST and MCP routes, citation engine, and SQLite indexing. No runtime Node.js, CDN, database daemon, or separate MCP process. Develop the browser frontend as a separately organized package behind the Rust service's HTTP/API boundary. Frontend code owns browser rendering, editor interaction and presentation state; Rust owns storage, identities, structure/history, authorization, validation, transactions and model credentials. The frontend must never directly read or write workspace files, sidecars, journals or credential stores.

**Separate development, single executable release:** provide a frontend build/development command independent of Rust compilation. During development only, a loopback frontend server may serve changing browser assets and proxy API/page-bootstrap requests to one fixed loopback Rust listener. Browser changes must become available without restarting the Rust service. Preserve unsaved buffers, draft acknowledgements and pending request identities when offering reload; a source rebuild cannot silently discard them. The development gateway validates its own exact Host/Origin and relevant CSRF/fetch metadata before any fixed-backend header normalization, rejects forwarded-header spoofing and arbitrary destinations, preserves cookies/status/streaming/cancellation, and exposes no workspace filesystem access. This narrowly scoped local development facility does not enable general reverse-proxy deployment (§4.4).

Release builds bundle the frontend's built HTML, CSS and JavaScript into the Rust executable and serve them through the same secured routes. End users run one binary; they need no Node.js, frontend server, source checkout, external asset folder or CDN. Retain reproducible generated assets and a versioned build manifest so Rust-only builds can consume verified checked-in artifacts; CI rebuilds and checks those artifacts against the frontend sources and shared application version. Development and embedded-release browser paths must exercise the same domain/API contracts and security behavior. Optional Pandoc conversion (§8.1) may use a separately installed operator-configured Pandoc executable; this explicit export-only dependency does not change the single Hypergraph server executable or the availability of ordinary Markdown export. Local use:

```sh
hypergraph --config ./hypergraph.toml
```

**Single-document launch workflow:** a Hypergraph PX process opens one greater document from a supplied local folder, or creates a new blank document in a new folder. Folder selection is a CLI/startup concern, not a document-selection dropdown in the editing interface. Opening an existing folder validates its workspace and bound document identity and opens that document on `main`; never silently select the first document by UUID or directory order. Preserve independently identifiable content nodes, transclusions and working branches within that document. Existing folders containing multiple document roots require an explicit, non-destructive migration/binding decision rather than automatic deletion or arbitrary selection.

For a new blank document, the CLI asks for its name and uses that name as the document's first Markdown heading (`# Name`). Validate the name as a single nonempty heading, without interpreting it as a filesystem path, shell command or Markdown instructions. Create the initial document, main branch and snapshot atomically through the shared domain initialization boundary; startup uses a separately identified local-operator initialization actor, recorded in the atomic transaction and folder binding, and must not impersonate an authenticated user or bypass audit requirements. This local-only authority can initialize an empty folder or bind an existing root; it cannot edit existing prose and is unavailable to browser/REST/MCP clients. Cancelled or interrupted prompts must not publish a partial document. Provide an explicit name argument for noninteractive use; missing input on noninteractive stdin must fail clearly rather than hang. Configuration remains available for service settings; a supplied document-folder location explicitly selects the content root.

The external TOML file controls the root storage directory and all service settings. If the directory does not exist, initialise it safely after validating location and permissions; if present, validate manifest/schema and recover or reject inconsistency without destructive auto-repair. Lock one writer per workspace. Paths are resolved relative to the config file where documented; explicitly configured absolute paths are allowed.

Proposed durable workspace layout:

```text
workspace/
  documents/           # editable ordinary Markdown
  fragments/           # promoted reusable Markdown fragments
  bibliography/        # optional imports/exports
  .hypergraph/
    manifest.json      # schema/workspace identity
    nodes/             # sidecars / mapping and graph metadata
    objects/           # immutable payload, revision, manifest and snapshot objects
    journal/           # transaction/recovery records
    index.sqlite       # rebuildable graph and full-text index
    auth/              # protected account/token records (not web-served)
```

Exact object/sidecar serialization and transaction-journal protocol require an ADR before durable document content is produced; existing workspace bootstrap does not define these formats. Prefer content-addressed immutable objects with a versioned cryptographic digest and canonical serialization. Separate logical revision events from payload digests: identical Markdown can share bytes without merging authorship, transaction identities or histories. Store revision envelopes, manifest states, provenance and snapshot closures durably; validate their hashes, ownership and references on load. A non-content-addressed mechanism needs an ADR demonstrating equivalent immutability/integrity and a migration path.

Committed immutable objects and journal head transitions determine historical state; SQLite contains only rebuildable indexes/caches. Current Markdown working files may contain a newer, uncommitted draft (§2.3). Persist their committed base, draft generation, ownership and checksums atomically through confined writes and recoverable metadata; acknowledged drafts survive crashes and index rebuilding without creating history entries. Missing committed projections can be rebuilt, but recovery must never overwrite a retained draft. Explicit commit atomically publishes content/composition/provenance/snapshot changes and reconciles the working draft; report projection or draft-reconciliation failures honestly and make retries idempotent. Detect external edits against recorded hashes and require reviewed import or conflict resolution; never silently discard working bytes or rewrite immutable history. Index rebuilding must recover committed timelines and provenance without network access.

### 3.2 Transaction and recovery invariants

Draft recovery retains acknowledged working bytes and their committed bases independently of disposable projections or indexes. Backups include recoverable drafts, clearly marked as uncommitted; restoring or rebuilding indexes must not silently commit them.

Journal stream tips establish commit ordering and visibility; they are distinct from same-node revision parents and branch-selected node revisions. Editing from an older revision on an isolated branch must not fabricate ancestry or require overwriting another branch.

One domain transaction validates all source anchors, expected content/manifest heads, permissions, ancestry and snapshot closure constraints under a consistent read view. Stage the complete write set: new immutable payloads/envelopes, manifest revisions, historical/provenance edges, structural change records, required snapshots, head changes and audit records. Publish visibility only after durable objects and a committed journal record exist; committed-state projections and SQLite are rebuildable from that commit, while separately persisted mutable drafts remain recoverable without publication. Readers must never see a new manifest without its referenced revisions, exact origins or required snapshot. Concurrent edits produce conflicts, not a mixed closure assembled from different head states. Shared-node content commits do not fan out duplicate node/manifest revisions to every referencing document.

Use confined staging, create-new object publication, checksum verification, durability barriers, commit markers, atomic replacement where supported and post-crash reconciliation. The ADR must specify exact ordering, commit point, locking/read-view isolation, acknowledgement and disk-full behaviour. Recovery exposes either the previous committed state or the complete newly committed state, never a partially applied structural/content operation. Replaying committed transactions is idempotent: finish interrupted projections and recreate indexes without adding duplicate revisions, snapshots or provenance. Quarantine/inspect uncommitted staging rather than treating it as history; missing/corrupt committed dependencies are integrity failures and must not be repaired by selecting current heads. Publish a health/integrity failure if recovery cannot prove consistency.

No arbitrary cap applies to any of the three history counts. Pagination and storage/work quotas do not justify silently pruning history: on capacity exhaustion, reject the proposed write atomically and retain earlier committed states. Default retention keeps all committed histories and snapshots. Any explicitly documented future retention/purge policy must preserve the entire dependency closure of retained nodes/revisions, snapshots, pins and provenance, including source ancestry, assets and citation snapshots. Removing a current inclusion or tombstoning a node does not make its historical objects disposable. Deduplicated objects can be reclaimed only after reference/retention analysis proves no retained record depends on them. Backup-archive rotation is distinct from deletion of primary history. V1 performs no irreversible history purge; any later operator-approved purge must disclose which recorded states become unavailable and preserve an audit record, never claim they remain reproducible.

Provide snapshot/checksum validation, operator-only backup/restore, dry-run integrity inspection and forward-only migrations with backup/rollback guidance. Backups include the retained histories and their complete dependency closures at one committed boundary, plus coherently captured working drafts and their exact bases; restore and index rebuild must reproduce recorded document states and provenance exactly. Test every durable-write phase with injected interruption, write/fsync/rename/publication failures and disk full, including failures between object publication, commit marker and projection/index updates. Document supported filesystem assumptions and acknowledge loss/corruption beyond those guarantees; never promise losslessness on unsupported/failing filesystems.

### 3.3 Future backup destinations and dissertation recovery

Provide an operator-controlled backup interface with local-folder/external-drive backup plus optional **Dropbox**, **Backblaze B2**, **Google Drive**, **Microsoft OneDrive**, and **Amazon S3** destinations. Additional S3-compatible services may follow through explicitly configured, reviewed adapters. Backblaze here means B2 object storage; compatibility with the Backblaze Computer Backup desktop product is not implied. Select the initial adapter order in an ADR; keep one portable archive format across destinations.

- Back up a consistent workspace snapshot containing Markdown, manifests/sidecars, all three retained histories and their complete dependency closures (§3.2), graph/provenance records, pinned citation metadata, required local assets, and clearly identified recoverable working drafts with their committed bases. Include a versioned archive manifest and checksums; SQLite remains rebuildable. Exclude credentials, tokens, session stores, transient locks, and caches that are not needed for recovery. Record required secret reprovisioning separately without storing secret values.
- Support explicit operator-triggered and scheduled backups, configurable retention, multiple destinations, and visible last-success/failure and restore-verification status. Keep a last known good backup; interrupted uploads, quota failures and offline providers must not block local dissertation work or delete valid backups. Use bounded retries and identify incomplete uploads distinctly from verified snapshots.
- Cloud connections are opt-in, with least-privilege provider credentials stored outside content and redacted from logs, archives, browser state, and MCP resources. Offer client-side encryption before upload; document key custody and recovery, and do not include decryption keys in the same archive. Validate provider endpoints, transport, size/time limits and any redirects through adapter-specific rules; do not expose an arbitrary network fetch service.
- Treat backup as versioned archival snapshots, distinct from live folder synchronization. A provider deletion or synchronized local mistake must not silently remove all recoverable history. Retention pruning is explicit, scoped to archives owned by this workspace, and preserves the configured minimum verified recovery points.
- Restore is an explicit operator action with integrity/schema checks and a preview, initially into a separate destination. Preserve stable IDs, node/composition/snapshot histories, exact derivation provenance and pinned citation/assets dependencies. Verify restoration offline on a fresh installation; never overwrite an active workspace or run imported content as code.
- Backup configuration, provider grants, restore, and retention deletion remain outside MCP tools. These are operator facilities, consistent with §3.2; a cloud connection does not authorize publishing dissertation content.

### 3.4 Future optional GitHub-backed file location

**Local filesystem storage remains the default.** A fresh install requires no GitHub account, repository, credentials, network connection or Git executable. Add an explicit optional GitHub storage setting so an operator can select a repository, branch and workspace subdirectory as the remote location for dissertation files. This is a content-workspace feature, separate from the application's own source-code repository and from archival cloud backups (§3.3).

#### Planned storage behaviour

- Retain a local working copy beneath the configured data root for editing, indexing and offline use. In GitHub mode, synchronize portable Markdown, durable sidecars, graph/provenance records, immutable revision and document-snapshot objects and their complete retained dependency closures, citation snapshots and supported assets with the selected repository. SQLite, temporary files, caches, credentials and authentication/session records remain local and excluded. Explicitly define handling of large files and repository limits before implementing asset upload; never silently omit required dissertation material.
- Keep Hypergraph node/revision IDs and append-only history independent of Git paths and commit IDs. File moves preserve identity. A Git commit records a synchronized workspace state; it is neither a document snapshot (§2.1) nor a replacement for any domain history, optimistic concurrency or provenance. Transfer objects first and publish remote state only when its retained snapshot/provenance closures are complete; reject history-rewriting or incomplete remote imports.
- Show local save state separately from remote synchronization state, including pending changes, last successful sync and actionable failures. Local saves remain usable offline. Interrupted upload, expired credentials and remote rate limits preserve the local committed workspace and pending synchronization work; never report a remote save before confirmation.
- Pull and push use an explicit common-base/remote-head precondition. Concurrent external edits produce a reviewable conflict; do not force-push, discard local revisions, rewrite immutable objects or silently choose a winner. Import remote changes only through shared domain validation and transactions, recording new revisions and reporting ambiguous identity/range conflicts.
- Present a preview before the initial upload or repository import. Selecting GitHub mode does not create a public repository, change repository visibility, overwrite an existing branch, publish unrelated local files or enable automatic background synchronization without an explicit setting. Recommend a private repository for unpublished dissertation content; verify access without disclosing secrets.
- Repository content is untrusted. Restrict imports to the selected workspace subtree; reject path escapes, symlinks and executable content. Do not execute Git hooks, filters, repository scripts, workflows or document instructions. Use an embedded reviewed library or a fixed backend adapter; do not add arbitrary Git/shell commands to REST or MCP. Validate provider destinations and confine outbound requests to the configured GitHub integration.
- Protect least-privilege, repository-scoped credentials outside content/configuration values and exclude them from logs, exports and backups. Connection management and remote publication authority belong to the operator. Existing browser/REST/MCP domain permissions still apply; choosing GitHub never grants an MCP actor write, credential or repository-management privileges.
- Support disabling GitHub and continuing with the complete local working copy without losing identities, history, citations or queued work. Switching repositories/branches requires a preview and explicit reconciliation; there is no automatic fallback upload to another repository. Repository synchronization is not a substitute for independently retained, verified backups.

#### Implementation sequence and acceptance

1. Record an ADR for local/remote authority, portable tracked-file rules, GitHub authentication, adapter/library choice, branch/subdirectory mapping, snapshot publication and conflict recovery. Define typed optional configuration and migration, preserving default local behaviour. Do not add unsupported keys to the current runnable config template.
2. Implement explicit connect/import and manual pull/push with scoped permissions, redacted status and common-base checks; exercise the adapter against fixtures before live integration.
3. Add opt-in scheduled/background synchronization only after interrupted-sync recovery, conflict review, offline operation and credential revocation tests pass.
4. Verify a second installation can reconstruct a synchronized dissertation workspace with the same IDs, revision/fork history and citation snapshots; validate that generated indices rebuild. Test concurrent edits, remote deletion/rename, interrupted publication, malformed repository content, excluded secrets, and return to local-only mode. Default local installs must make no GitHub requests.

## 4. Server, interfaces, and deployment

### 4.1 Process and routing

An Axum/Tokio-based Rust HTTP service is a candidate, with a frontend that may use a Rust/WASM framework or a small accessible browser editor component where justified. Major responsibilities: configuration/bootstrap, storage, graph/revisions, Markdown AST/source maps, composition/indexing, citations, auth, HTTP/REST, MCP adapter, embedded UI. Each transport calls the same `ApplicationService` methods; adapters do not directly mutate SQLite or the filesystem. Keep frontend source/build tooling in its own package and Rust HTTP handlers as transport adapters to the common application/domain service. Page rendering and asset embedding are packaging concerns, not a second implementation of storage or structural rules. Define and test request/response/error contracts at this boundary, including source ownership, expected heads, draft generations and exact request IDs. Frontend previews and optimistic state never establish committed truth independently of authorized backend receipts.

Canonical endpoint groups (names may be refined before implementation):

- `/` and `/assets/*`: embedded browser UI.
- `/api/v1/workspace`, `/documents`, `/nodes`, `/nodes/{id}/revisions`, `/nodes/{id}/forks`, `/graph`, `/search`, `/compositions` (including manifest history), `/documents/{id}/snapshots` (capture/list/read/reconstruct/restore), `/indexes`, `/exports`, `/citations`, `/zotero/status`. Exact route/action names may be refined without changing history semantics.
- Future comment/thread endpoints expose permission-scoped reads and shared create/reply/close/delete commands, with thread-state preconditions and no public-read inheritance for private discussion.
- `/api/v1/auth/*`: secure bootstrap, login/logout, principal/session and scoped agent credential maintenance.
- `/api/v1/conversations`, `/agent/actions`: permission-scoped conversation turns, attached targets, proposals, approval/cancellation, bounded progress streams and transaction reconciliation. Exact route names may be refined; these endpoints invoke the same authorized commands as REST/MCP editing.
- `/mcp`: embedded MCP Streamable HTTP endpoint.
- `/health/live`, `/health/ready`: minimal health diagnostics, no secret or graph content leaks.

Default greater-document endpoints resolve `main`; alternate branches and snapshots require explicit selectors. Expose branch list/create/read/compare/merge and append-only branch-head history through shared authorized commands when implemented; read/preview never creates a branch. Writes carry expected branch head as well as affected node/manifest preconditions. Autosave/action APIs also bind the submitted editor buffer version and preserve the mapping from the visible selection to committed source; acknowledgements must not replace newer local text or caret state.

Document endpoints expose typed schemas, idempotency identifiers where appropriate, `expected_revision` on writes, cursors for pagination, consistent errors, request limits, and no unbounded graph serialization. REST errors and MCP errors map to the same domain conditions. History queries select node, composition or snapshot scope and exact IDs, with stable bounded pagination and separate structural/content comparison. Read/reconstruct and preview are side-effect free; capture and restore persist records and require write grants. Multi-node edits accept expected-head maps for every affected identity and manifest; new identities use equivalent create preconditions. Responses include transaction ID, new revision/manifest/snapshot IDs, touched node/inclusion IDs, provenance effects and completeness diagnostics. Export accepts an existing snapshot ID or explicitly captures a consistent state, never silently resolves historical live references to current heads. Snapshot lookup is not authorization, and responses must not leak inaccessible history.

### 4.3 Authentication and initial setup

Authentication and distinct human/agent principal resolution are required for this dissertation app, including on loopback. The target default is `[auth].enabled=true`. A temporary unauthenticated development status/discovery mode must not expose private content, document writes, chat context or agent execution. Refuse unauthenticated remote operation or proxy publication. Bootstrap creates the initial human administrator only through loopback access or a securely provisioned short-lived setup token; never let the first arbitrary visitor claim the account. Bootstrap locks after success. Provision the second principal as a named non-admin MCP agent with explicit scoped/revocable machine credentials; do not expose its credentials in the browser or reuse administrator credentials. The agent may remain disconnected until its runtime is configured.

Passwords use Argon2id with per-user cryptographic salts and versioned settings; sessions are opaque CSPRNG-generated, hashed at rest, rotated on login, securely cookie-bound, revocable and expire. **Future requirement — persistent logins:** valid human browser sessions must survive normal application restarts, recompiles and crash recovery without requiring another login, until their original expiry or explicit logout/revocation. Persist session verifiers and expiry/revocation metadata securely in the local authentication store; never persist raw session tokens server-side. Use persistent browser cookies with matching expiry. Restart must neither extend expiry nor resurrect expired, logged-out or revoked sessions. Interrupted authentication-store writes must fail closed without losing acknowledged revocations. Keep sessions workspace-scoped and excluded from content exports, backups and GitHub synchronization. This concerns human login sessions; machine credentials retain their separate scope and revocation requirements. Apply CSRF/origin defences, rate limits/backoff, safe account recovery, redacted logs, and authorization to every document/history/search/export/conversation/MCP route. Enforce participant visibility on conversations and proposals. Roles initially include administrator and agent; grants are independently scoped to readable/writable content and operations. Additional human accounts and multiple agent users are reserved for the separate MU app (§1.3). Login does not enable MCP writes. Human approval does not elevate the agent beyond its own grants: delegated actions require the intersection of initiating-user permissions, agent permissions, operator policy and action grant. Recheck permissions and revocation immediately before commit, including after a long model response or approval delay.

**Public content visibility:** `[access].public_read` controls document content readable without login: `none` (default) keeps all content private; `main` permits reading the current greater-document main branch only; `all` permits reading current states of all document branches. This is a read-publication policy, not an authentication switch. Document writes, agent requests/approvals, conversations/prompts/replies, credentials, account management and administrative operations always require the appropriate authenticated principal. History/provenance enumeration and arbitrary node/object retrieval are not made public by a branch-view setting. An embedded dependency is disclosed only within the permitted branch's exact resolved view and scope; a public main view must not leak other branch revisions or a node's full history. Verify all required dependencies against the public-view scope; fail rather than substitute another revision or reveal an explicitly inaccessible dependency. Current permission revocation applies immediately; cache/stream behavior must not preserve access after a policy change takes effect. Settings apply on restart initially. Invalid values or unknown fields fail startup. Do not expose unpublished content or private paths through discovery while public reading is disabled.

## 5. Zotero as a built-in citation service

### 5.1 Default connection

For initial same-host desktop operation, use Zotero's **local REST API** at `http://127.0.0.1:23119/api/` from the Rust backend. Enable Zotero's setting allowing local applications to communicate. Read-only access should need no API key. Always send `Zotero-API-Version: 3`, where supported. The server probes Zotero availability; failure is nonfatal, with explicit disconnected/stale states and cached references available offline. Loopback refers to Hypergraph's host/network namespace, **not** automatically to a different workstation or container host.

### 5.2 Hosted option and constraints

Explicit `mode = "web"` uses HTTPS Zotero Web API v3 at the fixed `api.zotero.org` origin for configured personal/group libraries and protected read-only credentials. Never auto-switch local-to-web or transmit workspace text to Zotero. In v1 **all Zotero communication is read-only**, including when local APIs technically permit writes. Never implement an arbitrary URL fetch proxy; fixed destination allowlists, resolved-host validation, redirect refusal, bounded response size, timeout, pagination, rate-limit backoff, and concurrency limits apply. API secrets are not returned to UI or MCP clients.

### 5.3 Identity, caching, insertion, compilation

Use full `(provider, mode, endpoint_instance, library_type, library_id, item_key)` identity; local `Zotero-Server-ID`, when supported, distinguishes Zotero desktop libraries and protects against unintended instance changes (including mismatch responses). Do not equate local version numbers with hosted Web API version numbers. Fetch items/collections and normalise metadata to CSL-JSON while retaining original metadata and source version. Explicitly bound local pagination because the local API may otherwise return unbounded results. Protect against duplicate citekeys by deterministic workspace alias resolution.

Browser citation picker and MCP citation tools share one service: search items/collections, preview metadata, insert Pandoc-like `[@citekey, p. 12]` and multi-citations, and report missing/stale references. The compiler walks the composed document graph, gathers only cited items, performs CSL formatting through a maintained Rust library or vetted adapter, supports configured styles, and pins metadata snapshots in the document snapshot closure for reproducible exports. Historical reconstruction uses those retained records rather than refreshing Zotero; stale/missing cached metadata cannot silently change a recorded bibliography. Offline fallback import supports CSL-JSON/BibTeX/BibLaTeX; failure to resolve a citation must be visible rather than silently dropped. API response strings/URLs are untrusted and sanitized when displayed.

## 6. MCP: native model interface and discoverable design

### 6.1 Transport and architecture

MCP is served from the **same process and configured port** using Streamable HTTP at `/mcp`. Implement version negotiation against the current stable MCP protocol when developed; pin supported protocol revisions in a compatibility matrix and integration tests rather than hard-coding assumptions that could become obsolete. No separate MCP daemon, plugin runtime, or code execution capability is required. Both MCP and REST dispatch to identical domain services, transaction validation, citation resolution, and actor authorisation. Mutable draft APIs additionally bind authenticated actor, document/branch, exact committed base, expected draft generation and idempotent request identity. Draft persistence is separate from revision-commit APIs; agent clients gain no draft access or publication authority merely through discovery.

The in-UI agent integration has two separate responsibilities: a configured inference/conversation runtime produces proposals, and an MCP/domain command adapter executes only authorized operations as the agent principal. MCP discovery alone does not supply a chat model. Keep orchestration inside the single server executable where implemented; an external/local model service may be configured explicitly, without requiring a second Hypergraph daemon. The runtime may use an MCP client or the same internal application commands; both paths must enforce identical operator policy, agent/human grants, expected revisions and audit attribution. Never create a privileged in-process shortcut for UI-triggered agent writes.

**Provider and model selection:** providers and models are user-selectable through named profiles in the TOML configuration. OpenAI/ChatGPT support is the initial integration priority, with **ChatGPT sign-in/eligible plan access as the first live authentication path selected by the project owner**; the adapter boundary must allow other explicitly supported providers without changing domain editing/history commands. Each profile names a provider, exact model identifier and credential/authentication mode; the configured default profile selects the model for new turns. Do not hard-code a single model or imply all ChatGPT UI models are available to every integration/account. The owner selected `gpt-6.1-sol` as the current default and wants the latest supported model as the default selection policy. Resolve latest only from authoritative provider availability/recommendation metadata, within the explicitly supported profile family; never infer it from lexical IDs or catalogue ordering. Display and freeze the resolved exact model before dispatch. Preserve an explicit fixed-model override, never silently change an in-flight request/proposal, and fail clearly when latest cannot be resolved or is unavailable. Validate provider/model capability and account availability and report unsupported choices explicitly. Configuration changes take effect on restart initially; show the active profile/model in the UI. A model switch applies to subsequent turns, never an in-flight request or an existing proposal/action grant. Record requested and provider-reported model identifiers (when available), provider and profile per turn, preserving conversation, content and actor identity across switches. Keep conversation context portable; explain any required truncation or unsupported model features rather than silently losing context or changing permissions.

**Persistent agent connection:** once explicitly connected, retain the selected provider/model profile and supported credentials securely across browser reloads, application restarts and recompiles. Reuse valid authorization and refresh expiring tokens through the supported provider mechanism without requiring routine sign-in. Token rotation must be durable and recoverable; never expose credentials in document files, browser storage, transcripts, MCP responses, logs or backups. Persistence does not extend provider expiry, bypass revoked authorization or enable a disabled runtime. After transient network interruption, reconnect with bounded backoff and display accurate connected/reconnecting/offline/sign-in-required states. Persist conversation and task identities independently of the transport connection. Reconcile interrupted requests and committed outcomes before retrying; reconnection must never replay an edit or silently resubmit an uncertain model request. Explicit disconnect removes usable local credentials and stops automatic reconnection; cancellation and provider revocation remain effective after restart. Browser login and provider authorization are separate lifecycles: only an authenticated, authorized application user may use a retained connection. A persistent connection need not keep a network socket open continuously.

Distinguish OpenAI API-key access from supported ChatGPT sign-in/plan-based inference. Verify integration eligibility, required scopes and model availability before offering the latter; identity-only ChatGPT sign-in does not authorize inference. Do not reuse browser cookies or promise subscription access merely because a user has ChatGPT. API-key access and any supported plan-based access must be explicitly selected; never silently switch billing/authentication paths. Credentials remain server-side environment references or protected credential-store entries.

The runtime ADR must settle adapter/request contracts, supported authentication paths, local versus hosted inference, permitted outbound destinations, context disclosure, streaming/cancellation and error/cost budgets before integration code. External transmission of dissertation text requires explicit administrator configuration and visible disclosure. No automatic provider fallback or document-specified destinations. Mock runtime tests must exercise the complete proposal/approval/commit flow without network access.

### 6.3 MCP tool surface

The fixed built-in operator catalogue is non-private descriptive metadata and may be exposed with discovery guidance. This does not expose workspace-defined operators, logical links, operands or content without authorization.

Reconstruction reads only the named snapshot closure under current permissions; preview returns an ephemeral view without persisting a snapshot.

Write-capable when authorised: `create_logical_link`, `update_logical_link`, `remove_logical_link`, `create_branch`, `merge_branch`, `create_document`, `edit_node`, `promote_selection`, `fork_node`, `create_composition`, `update_index`, `insert_citation`, `split_node`, `merge_nodes`, `edit_composition` (insert/remove/reorder/reuse/pin with multi-manifest moves), `capture_snapshot`, `restore_snapshot`, `export_document` (filesystem side effect), `insert_text` (exact cursor anchor), and `restore_revision`. Never retry non-idempotent writes automatically. Publishing, secret management, bootstrap, filesystem command execution, arbitrary URL fetch, unrestricted SQL, and shell access are **not** exposed as tools.

### 6.4 MCP security

`mcp.enabled=true` and `mcp.write_enabled=false` by default. Unauthenticated loopback discovery is limited to non-private status/guides. All content reads and agent execution require a resolved principal. MCP uses appropriately scoped/revocable actor tokens or compatible OAuth—not browser session cookies as a substitute for machine permissions. Global write enablement is necessary **but not sufficient**: actor must have an explicit write grant, and sensitive actions need independently verified approval/action grants when client confirmation cannot be trusted. Reject bootstrap/login through MCP. Validate Host and Origin; protect against DNS rebinding, proxy spoofing, CSRF-like local-service access, prompt injection, oversized tool results, and traversal budget exhaustion. MCP tool annotations are informative, never substitutes for server checks. UI-triggered agent actions obey the same gates; a trusted server-side approval record binds the human, agent, proposal digest, exact targets/preconditions and allowed operation. A client-supplied confirmation flag is insufficient. Test compatibility with MCP Inspector and another independent client.

## 7. Trust, security, and operational safety

### 7.1 Threat model and invariants

Primary adversaries: malicious Markdown/HTML, Zotero strings and links, prompt-injection content, unauthenticated web clients, compromised MCP clients/tokens, malicious workspace file names/symlinks, network attackers behind misconfigured proxies, and dependency/supply-chain compromise. The goal is defence in depth and bounded risk, **not a claim of absolute prevention of remote code execution**.

- Parse Markdown into a documented AST; render using context-safe escaping and strict HTML sanitisation or disable raw HTML by default. Safe URL schemes only (`javascript:`, `data:`, unsafe embedded SVG/scripts prohibited). No use of unsanitized `innerHTML` or unsafe DOM sinks.
- No document-supplied shell calls, dynamic evaluation, native plugins, executable templates, command injection, or SQL string interpolation. Parameterise database operations.
- Restrict filesystem IO beneath the configured data root using symlink-resistant/handle-relative traversal where available; prohibit `..` escapes, unsafe hard links, TOCTOU-prone prefix checks, and unvalidated output names. Keep `.hypergraph/auth` and service files unreachable through web routes.
- Apply strict HTTP body/stream limits, timeouts, concurrency caps, Origin/Host verification, deny-by-default CORS, CSRF prevention, fixed outbound Zotero origins and explicitly configured model-service destinations, no unreviewed redirects, and safe `Content-Type`, `Content-Disposition`, `nosniff`, CSP, and other relevant headers.
- No remote asset loading by default. If attachments are introduced, check declared and actual file type, quotas, storage permissions, executable types, and sanitised download behaviour.
- The styled source editor renders visible Markdown syntax and untrusted HTML as safe text/decorations, never executable HTML. DOM decorations and clipboard content cannot inject scripts, create permissions or change source ownership; validate rendered-to-source ranges and source version at the shared command boundary.
- Treat document text, selected excerpts, model responses and retrieved context as untrusted data; none can expand target scope, grant permissions, request secret disclosure or change provider destinations. Bound agent turns, context/result size, concurrency and execution time. Render chat/proposal text safely; do not execute model-supplied HTML or code.
- Never log secrets, authentication cookies/tokens, Zotero API keys, raw Markdown bodies, or sensitive private graph content by default. Structured audit logs should contain action IDs, actor, targets, outcomes, model attribution references for MCP/agent changes, and redacted errors.
- Authorize historical revisions, derivation navigation, snapshots and every included dependency under current actor permissions; immutable snapshot IDs/digests never grant access or revive revoked grants. If any required dependency is denied, exact reconstruction/export fails without substituting current/public content or disclosing the private closure. Redacted partial previews must be labelled incomplete and cannot claim historical equivalence. Shared object deduplication must not expose cross-scope existence or bypass authorization.
- Validate object hashes, revision ownership, inclusion targets, snapshot closure completeness and ancestry when importing/restoring/rebuilding. Never execute historical Markdown or provenance metadata; render historical views with the same protections as current content. Immutable storage detects corruption; it does not by itself protect against a hostile privileged filesystem writer. Recovery never silently rewrites committed history or treats an index as source authority.
- Least-privilege OS process, locked dependencies, cargo audits, fuzz/property tests for parsers and graph/history operations, and repeatable backups/recovery drills.

### 7.2 Runtime and build protection

Integrate current maintained Rust security practices, `unsafe` restrictions and review, dependency licence/vulnerability checks, no embedded credentials, CI lint/format/test checks, SBOM publication, and signed/checksummed release artifacts where feasible. Target acceptable baseline latency and resource use via profiling and published benchmark fixtures rather than unverified performance promises.

## 11. Decisions requiring ADR before coding

Existing decisions remain in force: executable `hypergraph` and the current pinned MCP transport revision (ADR 0003), UUIDv7 identities (ADR 0004), and AGPL-3.0-only application licensing (ADR 0002). These do not settle document-history serialization or justify treating the bootstrap manifest as a document snapshot.

**High-priority future architecture investigation:** Resolve the question: *What mathematical and design principles should guide the system's structural and logical internals to achieve efficiency, speed and simplicity of design?* Prioritize this investigation before further durable history/transaction and compiler architecture decisions; revisit its conclusions as benchmark evidence becomes available. This is a research/design task, not a presupposed choice of a more complex implementation.

Evaluate graph theory and DAG invariants; persistent/immutable data structures and structural sharing; content addressing and Merkle-style dependency graphs; algorithmic and amortized complexity; incremental computation and dependency invalidation; database normalization, indexing and query planning; transaction/state-machine models; and minimal interfaces with a single source of authority. These are candidate principles to assess, not mandatory technologies. Explain how each selected principle simplifies or improves actual domain operations and where its costs outweigh its benefits.

Produce an ADR comparing a small set of concrete designs against representative dissertation workloads: many small reusable nodes, deep/repeated transclusions, long histories, extraction/split/fork/merge, snapshot reconstruction, search and index rebuilding. Record expected time/space complexity, measured latency/throughput, memory/storage/write amplification and recovery cost. Assess simplicity through the number of authoritative representations, maintained invariants, synchronization boundaries, special cases and migration/testing burden. Prefer the simplest design that meets measured budgets; avoid speculative optimization. Preserve stable identities, the three immutable histories, exact provenance, deterministic reconstruction, authorization and bounded graph expansion. Acceptance requires reproducible fixtures/benchmarks, explicit tradeoffs, chosen principles and deferred alternatives; optimization must not silently weaken correctness or existing guarantees.

Before implementing durable document histories, approve ADRs for:

- Canonical object/envelope/sidecar encoding, cryptographic digest and hash agility; distinguish logical revision-event identities from deduplicated content addresses.
- Consistent read-view isolation, multi-head compare-and-swap, durable journal/commit ordering, acknowledgement, projection reconciliation and failure recovery on supported filesystems.
- Document branch identity, default-main initialization, append-only branch-head transitions, isolated branch read views/live dependency capture and merge semantics; preserve shared node histories and exact snapshot closures without advancing unrelated branches.
- Snapshot closure addressing and binding-context/subtree-pin representation, including repeated use of the same revision under different closures; retain the semantics in §2.1.
- Reconstruction-profile version compatibility and migration, preserving the ability to read original snapshots; retention reachability and integrity/backup verification mechanisms.

The next primary-editor ADR must choose the editor component and source document model, visual decorations that retain syntax, mappings for composed/local/transcluded content, platform shortcut map, selection-to-action handoff, five-second draft debounce/IME rules, explicit commit boundaries, buffer-version acknowledgements, working-file/draft reconciliation and recovery. It must implement §2.3 and acceptance 35; choosing a component must not weaken those requirements. Library choice and exact supplementary shortcuts remain implementation decisions, not reasons to defer the `0.1.0` gate.

Other implementation ADRs still cover the editor/source-map component, citation-style library, trusted-proxy representation, backup archive/encryption/retention and adapter order, Pandoc invocation/Word templates, optional GitHub synchronization/conflict mechanisms, and initial human/agent delegation and concurrency mechanisms. Multi-human membership/sharing and multiple agent users belong to the separate MU design (§1.3). Prioritize a human/agent authorization ADR, Unicode/Markdown selection and cursor-anchor ADR, and UI agent runtime/orchestration ADR before further authoring endpoint work. Resolve provider adapter/runtime mechanisms and supported OpenAI/ChatGPT authentication, local/hosted deployment, context disclosure, credential storage, target-bound approval, streamed job lifecycle, persistent connection/token refresh and reconciliation. Real-time coauthoring remains a separate future decision. These mechanism decisions must implement §§2–3 without weakening immutability, exact reconstruction or shared-source independence. An ADR can refine mechanisms; changing requirements requires a reviewed revision of **this specification**, not an independently authoritative addendum.
