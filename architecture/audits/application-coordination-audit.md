## Scope and existing coverage

The engine box **Application coordination** opens the stable `c3_application` view. Its five coordination responsibilities previously led to general API views or sequences, leaving their own implementation coverage implicit. Feature boxes reuse existing document/provenance/reference/annotation responsibilities; they are not new services. [Workspace](../../crates/storage/src/lib.rs) hosts application orchestration together with storage today: no separate application crate, command bus or common query facade exists.

The audit retains that C3 and its original boxes/17 curves. Four explicit return connections now show admission errors, authorized replay/conflict, published receipts/errors and protected read results/errors returning through Runtime/API. The canvas widens for those returns; original node, curve and label coordinates remain. Inputs are the existing frozen-command and direct-query connections. The caller remains responsible for session/unlock and wire response handling; a database result does not prove browser observation.

## Enforcement and workflow findings

The publication protocol's **§4 planned mutation/recovery**, **§5 draft autosave**, and **§6 explicit Commit** constrain the writer spine. Domain/navigation **§3 proposed navigation contracts** and **§11 planned workspace/reuse queries** describe broader obligations than the bounded current APIs. OWNER009 retains portable workspace evidence and accepts that a complete authentic rollback is not detectable using evidence restored with it. OWNER010 supersedes explicit-user-action-only prose for the two adopted logical departure boundaries; browser orchestration performs that decision, not the server's generic Commit operation. ADR019 governs working branches/private checkpoints; staged parent-Merge owner directions are not proof that two-parent execution exists.

1. `validate_command` runs before serialization/digest and the immediate transaction. Supported schema and current catalog owner/device are checked. `authority::command` plus branch/working-family source checks precede receipt lookup. These are several existing checks, not one new authorization component/function.
2. Digest equality concerns **adapter-serialized Command**, not raw HTTP JSON bytes or a new canonical wire format. A matching original receipt is reauthorized through `authority::outcome` before return, ahead of mutable generation/head preconditions. Only NotFound allows new execution; corrupt receipts fail closed. The receipt-only query independently rechecks current catalog/outcome scope.
3. Feature helpers stage effects in the caller's transaction. The result and original receipt are inserted before `tx.commit`. Pre-COMMIT failures do not publish partial staged effects. A process/reply loss around COMMIT cannot justify fresh intent. The production checkpoint closure is no-op; test-only failure/exit after the committed checkpoint must not be described as rollback.
4. Original Save preserves owned UTF8 text/line endings and updates draft generation/sequence; it creates no revision. Commit checks exact captured generation/base/sequence, publishes same-node parent history and exact retained snapshot, updates head/draft and promotes matching checkpoints. Server Commit itself does not enforce the browser's skip-unchanged departure policy.
5. WorkingCopy freezes an exact owned draft/range/quote, validates its current generation/base/sequence, then stages both private checkpoint and clipboard reference. A stale/full private list aborts the checkpoint too. A later matching text Commit retains the private origin and adds promotion evidence. Browser private-list replacement is a separate operation; its failure cannot undo already committed text.
6. Protected reads are direct Workspace entry points. Transactions, page/work budgets, catalog checks and result closure are method-specific; some call authority helpers and others perform equivalent local checks. The C4 authority-context edge is not a fabricated common call. Exact reconstruction rejects missing/mismatched data instead of following current heads.

New model relations can change inherited dynamic-step styles; fourteen existing messages now explicitly retain their previous styles. The reused Fork sequence keeps its messages/appearance even though inferred relationship metadata changes. The named sequences expose guards/errors and link the reused Save, Commit, original-request recovery and Fork workflows. They are source-derived descriptions, not new execution services or exhaustive traces of every feature mutation. Cancellation does not imply rollback of a request that may already have committed; no server-side cancellation protocol is invented.

## Discrepancies, evidence limits and open V3 questions

- Broader composition/occurrence navigation, general multi-owner edits, general grants/disclosure/egress policy and full closed-snapshot expansion remain outside the ordinary one-owner/one-occurrence implementation. Exact single-occurrence snapshots do not discharge every general closure obligation. Reference cycles remain distinct from expansion-cycle rejection.
- Immutable same-node history and cross-identity derivation stay separate. Existing derivation/publisher evidence does not establish original authorship. Parent-Merge planning/experimental single-parent temporal publication do not establish integrated two-parent publication or normal schema3 opening.
- Required future projections/rebuild, federation convergence, full crash/power-loss coverage and recovery acceptance are not delivered by SQLite WAL/FULL or operation receipts. OWNER009 rules out an external witness; no witness is added.
- Browser pending intent is retained for retries, but this audit does not establish durable recovery of all unsent typing/frozen IDs after browser destruction. No plaintext browser persistence or substitute operation is introduced. Lost session/unlock replies and launch recovery remain separately bounded Runtime/frontend questions.
- Should V3 retain co-location or define explicit interfaces between planning, authorization and persistence? What protocol/versioning rules should govern command digests and receipt compatibility? Which feature families should share a query budget contract? What accepted upgrade/integration contract should expose experimental temporal methods? These are owner decisions, not selected refactors.

[Test sources](../../crates/storage/src/lib.rs) cover restart/exact source/retry, stale writers, rollback and process-exit checkpoints; [authority tests](../../crates/storage/src/authority.rs) cover revoked inputs and replay-result scope. Working-reference tests cover capture/promotion and atomic failures. The [formal digest](../../docs/08-assurance/formal-validation-digest.md) distinguishes checked graph models and one extracted Rust helper: none proves Workspace transactions, authority, feature publication, filesystem behaviour or this architecture. Tests/proofs were reviewed, not run, and their historical evidence is not renewed.
