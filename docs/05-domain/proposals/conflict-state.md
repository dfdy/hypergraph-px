## 1. Authorised alternatives, preference and millisecond comparison

A changed followed source can present distinct exact competing selections. Freeze the acting workspace user, affected composition/private context, precise inclusion/use, current selected candidate and authorised alternatives before choosing. Each candidate retains exact source state, selected descendant environment and byte-affecting interpretation; revision alone or equal source bytes cannot stand for them. Historical closed reads never refresh selections. Missing/denied/corrupt inputs are item1 failures, not invitations to omit a contender or read a newer head.

Preference is per workspace-local user, **Ask by default**. Automatic latest timestamp is explicit opt-in, read when preparing a new intent. Changing preference does not retarget pending/frozen operations, another user's choices or historical selections. Unsupported/invalid preference never enables Automatic. Backend checks apply through browser and MCP; a disabled button, map token, workspace unlock or selected source is not authority.

### Timestamp representation and provenance

HPX records the actual supported server clock sample when finalising a **new committed version's publication transaction**, and persists that sample with the exact version/publication evidence in the same atomic boundary. This is HPX's recorded Commit time, not a promise of the exact physical fsync instant. Failed/rolled-back attempts publish no Commit timestamp. No-op/receipt replay or accepting an existing version retains the original timestamp; it does not make that version newer. Ordinary autosave/working evidence has no invented Commit time. Existing records without timestamps remain missing; no migration backfills from filesystem/Git/SQL dates, device assertions, import order, current time or inferred ancestry.

`epoch_ms` is a canonical signed64 decimal **string** of Unix UTC milliseconds, range −9223372036854775808..9223372036854775807; no `+`, leading zeros, whitespace, exponent, decimal fraction or negative zero. Parse with checked integer arithmetic/BigInt, not floating-point milliseconds. Derive milliseconds by floor of the observed Unix time, not nearest rounding; e.g. +1.999ms→`"1"`, −0.001ms→`"-1"`. Preserve the recorded integer thereafter. This format precision is not measured clock accuracy or causal order.

A CommitStamp is `recorded`, `unreliable` or `unavailable`. Recorded/unreliable samples retain actual observed milliseconds and the clock-basis/sample evidence; unavailable has null milliseconds/sample and an explicit reason. A clock basis is a workspace-local engine clock epoch, not another user/provider/account or a source identity. A restart or unestablished monotonic-clock continuity starts a new basis. A detected backward jump, unsupported sample, contradictory monotonic bracket or discontinuity makes the affected sample/basis unusable for Automatic; never clamp the time or fabricate a later timestamp.

For concrete initial health evidence, bracket each wall-clock sample with monotonic readings from that continuous process. Retain the two monotonic readings as unsigned decimal nanoseconds and the wall-clock integer. Require before≤after and established same-process basis. Compare the elapsed monotonic interval between consecutive brackets with the quantisation interval permitted by the two millisecond wall samples; a demonstrably disjoint interval records discontinuity. This supplies an observable reason for refusal, not proof of external clock truth: undetectable skew and an inaccurate but stable clock remain possible, and clock time stays a heuristic. No NTP/provider connection, user clock-tuning control or arbitrary numerical drift tolerance is introduced. Failure to establish the evidence falls back to Ask.

### Comparison decision

A single consistent protected read obtains candidates, their actual version/publication bindings, timestamp records, current time-basis usability and preference. Automatic is permitted only if every distinct competing candidate has a valid HPX-recorded stamp, supported identical time scale, matching workspace/basis and usable quality. Compare exact signed integers. Different/unverifiable clock bases, unavailable, unreliable, malformed or incomparable times **Ask**; do not drop the offending candidate. Unavailable authority/input remains a truthful protected-input failure, not a timestamp fallback that bypasses access.

| Condition | Result |
| --- | --- |
| Ask preference | Request an explicit choice among authorised exact alternatives; preserve acknowledged work meanwhile. |
| Automatic; all competing times supported/comparable and pairwise distinct | Select the strictly latest integer time as a definite selection, retaining an **unresolved** review issue and comparison marker. No automatic Commit. |
| Equal timestamps on competing candidates | Ask, including an equal pair in a larger candidate set; no ID/order/device/ancestry tie-break. |
| Any missing/unreliable/incomparable time | Ask with the truthful permitted reason; no backfill, silent replacement or automatic exclusion of a contender. |
| One exact candidate; duplicate enumeration only | Validate and collapse only exact duplicate references in that same comparison intent, not equal-text/different-state candidates. No competing choice merely from duplicate enumeration. |

The captured decision records the actual candidate/stamp/basis observations used. Revalidation before publication establishes the same frozen candidate bindings and current authority; it does not rerun the old intent against newer heads/times. If fresh evidence invalidates a pending automatic choice, report the conflict/fallback and retain the last acknowledged state; never rewrite already committed selections retroactively. Ask's version choice is not itself resolution unless the user explicitly names the issue and requests resolution. Viewing or comparing never resolves.

## 2. Conflict identity, exact anchors and visibility

Allocate one workspace-local opaque `ConflictId` per actual review issue, through the existing application ID boundary. It is a review identity, not a Node/Revision/Occurrence ID. The immutable issue freezes its initial candidates, selected candidate/decision basis and exact affected context. Repeated uses selecting the same source can have different conflicts; different candidate sets/problem scopes are not merged because a sentence/paragraph/section overlaps. Genuinely new competing selections create a new issue with an explicit optional relation to prior issues; recency does not resolve or supersede an old issue.

Reuse item3 `Id32`, `RecordRef`, `Range`, `Position`, `SourceRef`, local32 indexes and exact source/interpretation validation. A `Candidate` is `{source:SourceRef,selection:{bundle:RecordRef39,row:L32}|null,range:Range|null,publication:RecordRef|null,time:RecordRef45|null}`. A nonnull selection binds descendant/context choices; null is valid only for a complete exact owned-source state without a composite selection. A nonnull range always refers to full owned UTF8. Time records require the actual matching committed publication; private working alternatives without one Ask rather than masquerading as committed. All fields remain typed, kind/version/owner/context checked and authorised.

`VersionContext` is tagged `{kind:"committed",document,bundle:RecordRef39,publication:RecordRef}` or `{kind:"private",user,document,branch,draft,generation,sequence,bundle:RecordRef39,recovery:RecordRef41}`. Committed context includes actual publication evidence, not a name supplied by a viewer. Private context retains its ordinary visibility. This does not define new workspace-user identity/permission formats; actual supported suppliers must establish those fields.

`Anchor` is `{bundle:RecordRef39,action_root:L32,steps:[L32],fragment:L32,location,region_hint}`. `steps` follows actual selected include **part indexes** from the action root; verify each occurrence/target and reconstruction/cycle boundary under item3. It is a composition-local durable locator validated against the bundle, not a cached use index/global occurrence ID. `location` is `{kind:"owned_range",source:L32,range:Range}` or `{kind:"structural_range",start:Position,end:Position}`. `region_hint` is `sentence`, `paragraph`, `section` or `structural`, a presentation summary, not a persistent node/ownership claim. Preserve before/after zero-byte positions and exact partial fragments; no source normalization, fuzzy quote search or nearest-text relocation.

A marker summarises a **set of named issue identities attached to the exact viewed version**. Resolving one changes only that issue's status; other overlapping/adjacent issues stay visible. An explicit batch lists exactly the issues and chosen outcome for each. UI grouping cannot create one synthetic resolution identity or clear every issue in a visual region.

Shared committed-version markers are visible to every authorised viewer of that version regardless of preference. Private issues/drafts/notes do not become public simply by committing another document or opening comparison. Publishing a private review context as shared requires the normal authorised publication boundary and a disclosure-safe shared issue; private-only evidence/lineage stays private. Do not relabel a private issue record as public. An explicit publication may establish a new shared issue with private correspondence retained only in the private context; its fresh identity must not erase the original private history.

Stored evidence can refer to alternatives/outcomes that a particular viewer cannot inspect. Backend disclosure supplies the shared issue/status permitted for the affected version and only authorised detail; no hidden candidate bytes, private note, inaccessible identity/count or guessed authorship is leaked. A comparison may report unavailable detail under normal policy. Marker presence never grants source/resolve rights; required current workspace-user permission checks remain mechanisms to implement, not an invented administrator role or per-node ACL.

## 3. Orthogonal states and explicit resolution

Maintain three separate axes: exact **selection** (undecided/definite), per-issue **review** (open/resolved), and attachment **correspondence** (exact/uncertain). These are semantic states, not a new wire error enum. A definite automatic selection can be open; a historical source stays identical while its current review status changes.

| Action / precondition | Resulting state / effects |
| --- | --- |
| Detect a new competing issue | Immutable issue plus open head. Freeze candidates/anchor and the decision evidence; initial Ask leaves selection undecided until normal choice, Automatic can make it definite but open. |
| Open comparison, navigate, read history, change preference | No resolution write, no content mutation or issue clearing. |
| Explicitly accept selected candidate | Resolve that named issue after authority/current-open checks; selection/content need not change and no content revision is required. |
| Explicitly choose an existing alternative | Use the exact named authorised candidate. If this changes content/selection, complete its normal Save/Commit workflow first or atomically within an actually supported normal operation; then record the exact resolution outcome. Do not invent a Commit just for review. |
| Explicit edited result | Edit through normal owned-source/graph operations, not a generic multi-owner buffer write. Establish the exact acknowledged/published result and actual evidence before final resolution; unacknowledged typing is not a result. Preserve current scoped Save/Commit behaviour and OWNER050's unresolved universal coupling. |
| Failure/stale state/cancellation before resolution publication | Keep issue open and last valid view/acknowledged work. A separately completed content change remains real; do not pretend it rolled back because a later review write failed. |
| Concurrent resolution already committed | A matching original operation reconciles its stored result. A different stale intent conflicts and returns the actual permitted status; it does not silently replace, merge or claim the other user's resolution. |

Resolution outcomes are strict variants `{kind:"accept_selected",candidate:L32}`, `{kind:"choose_existing",candidate:L32,result:Candidate}` or `{kind:"edited_result",result:Candidate}`. For the first, candidate equals the original selected candidate or an exact validated continuation on the reviewed attachment. Choosing an alternative must identify an existing issue candidate and its actual resulting context; edited result retains its own exact evidence. No claim that a chosen candidate is true, causally later or semantically agreed follows. Retain actual resolving workspace user, issue identity and outcome, plus optional UTF8 note. Note absence is allowed; no mandatory explanation or authorship inference.

Final resolution is an immutable event and a checked open→resolved head transition. This initial design has no automatic reopening or silent re-resolution; new competition creates a new issue. A request that disagrees with an already recorded result reports it and requires a separately explicit normal content/selection intent; it cannot rewrite the first event. Additional review corrections/reopening are not inferred as an implemented capability. Resolution can pin exact private checkpoint/working outcome material as required durable review evidence under OWNER052, without renaming it a RevisionId, exposing a private result or creating permanent history merely per autosave. Actual immutable-reference capture/acknowledgement suppliers must exist and be validated before success; otherwise the resolution remains incomplete/open.

## 4. Shared current history, carry-forward and uncertain mapping

An immutable version attachment states **where an issue applies**; a separately checked issue head states its **current shared resolution**. Historical source reads use the exact bundle/source bytes and then a current authorised review overlay. Do not freeze “unresolved forever” in authored text or mutate a snapshot to clear a marker. Historical views label current status and link to accessible original issue/decision/resolution history, including the actual resolving user, chosen exact outcome and optional note subject to ordinary disclosure.

If an as-of review view is offered, label it as such and bind an explicit per-issue review-generation cutoff. An open-at-generation0 view differs from current resolved-at-generation1; wall-clock display dates alone cannot establish that cutoff. A vector of issue cutoffs is not a globally atomic historical review snapshot unless separately established. Current read results likewise identify their coherent review heads; delayed responses cannot roll a newer local status or typing backward. Resolution history is metadata, not a byte-affecting reconstruction dependency.

Carry an existing issue forward **only when exact correspondence establishes the same problem**. Validate the old/new immutable bundles, source/selection/interpretation, actual occurrence-chain relation, candidate scope and every fragment/structural endpoint. Two supported proof shapes are specified:

- **Exact selected-context correspondence:** a checked finite row/source/structure mapping preserving actual source bindings, ordered selected contributions/targets and relevant occurrence identity, with local references translated explicitly. Bound graph comparisons, including cycles. Do not equate local row numbers from different bundles, apply a bisimulation quotient or change the accepted recurrence rule.
- **Unchanged-scope edit correspondence:** actual supported authenticated edit/structural-transition evidence proves which exact old/new full-source ranges and positions correspond and that the issue's relevant selected content/competing alternatives did not change. Retain that evidence and exact before/after bindings, not a boolean or matching quote. An unrelated parent edit can move an inclusion's ordinal while preserving its occurrence/selected target. Where source revision changes outside the issue, an explicit candidate-continuation mapping preserves the original candidate identity/history and names the exact new state; do not rerun Automatic on its later timestamp.

An attachment records the new anchor plus original→current candidate continuations and exact correspondence evidence. It does not mutate the issue's frozen original candidates. A genuinely new competing selection/content/problem creates a fresh issue, with any prior relation explicit; there is no blanket “latest issue wins” or implicit resolution of the old issue.

If correspondence is unavailable, partial, ambiguous, denied or beyond resource allowance, **do not guess an anchor or drop unresolved context**. Retain the old attachment/issue and a separate carry-evidence record naming the new version/context, with `uncertain` relation and bounded reason. The new view shows an authorised document-level “review correspondence uncertain” indication and link to the exact prior context; it does not assert that the old issue applies at a guessed new range. This state does not itself invalidate acknowledged source or add a new Commit prohibition: normal source publication may proceed only under its existing guarantees, with uncertainty retained and reported. Resolution of the old exact issue does not prove uncertain new-context correspondence; keep that distinction visible until actual evidence establishes it or a concrete new issue is recorded.

Unrelated edits must therefore result in a verified carry or visible retained uncertainty, never silent marker disappearance. Regional summaries count exact open attachments and correspondence uncertainty separately; counts/details remain subject to authority. Source/selection/history retention, not an evictable cache, supplies these references. No cleanup/deletion policy is added.

## 5. Stale, concurrent, idempotent and crash recovery contract

Prepare one immutable intent with actor/context, exact issue IDs, attachment/version bindings, current open-head generations, outcomes/notes and any result-operation evidence. Browser/MCP clients use the same logical backend policy. A semantic comparison modal or cached “open” boolean is not a precondition token. Backend validates actual current workspace-user authority for affected resources and disclosure before protected replay/new publication; no grant is inferred from possession of an issue ID.

An explicit batch rejects duplicate issue IDs and names one action per issue; sort by exact issue bytes for canonical serialization and lock/CAS ordering. All named issues must validate and resolve in one supported atomic review transaction, including immutable resolution records, their head changes and the original-operation receipt. If any member is stale/denied/invalid/over-limit, no member is reported resolved by that batch. Do not split a batch into secretly partial successes or clear unlisted siblings. A content/result operation may already have succeeded separately under normal semantics; preserve and report that fact.

Proposed orchestration stages are prepared→awaiting_result→result_acknowledged→awaiting_resolution→settled. Accept-selected/no-content-change can skip the result stage. When the actual normal application offers a combined atomic operation, use its real boundary; do not claim one from WAL alone. Otherwise retain a private pending intent, reconcile the normal content operation first, and submit/reconcile the review operation against its exact established result. Unknown content or review outcome remains unknown, not a failed/no-op guess or reason to send a changed body under the same operation ID. A browser loss of pending state does not erase authoritative server review heads; reopen by reading exact current evidence, without pretending the lost request executed.

Matching original operation ID/body returns its actual authorised original receipt even if another view has advanced; changed body/context/actor under that ID conflicts. A new stale resolution operation cannot report success merely because someone else resolved the issue. One succeeds at the open-head compare-and-set; the other refreshes truthful status. Do not use Commit time or request arrival timestamp to merge concurrent resolutions. Late replies establish only their exact old operation; preserve newer typing/selection/status and do not retarget current source.

Bound source acquisition, candidates, anchors, comparison/edit proofs, issue sets, notes, history pages, CAS/receipt work and browser overlay costs under item2. Resource refusal preserves the last valid view and exact frozen context, never manufactures a cycle stop, resolves an issue or drops shared history. Crash/failure before atomic review commit yields no partial resolution; crash/lost reply after commit reconciles the original receipt/head/history. A stale/disconnected UI does not free still-running resources or authorise an automatic retry chain.

Item2 pre-work allowances cover encoding expansion, retained observations/proofs/notes and full receipt size. Oversize records/batches explicitly refuse; no unspecified chunking, partial resolution or history truncation. Source snapshots and item3 bundles remain byte-identical; dynamic review status is outside source-emission interpretation and derived source-map equality.

### Fit with item3's incompatible profile

Keep item3 candidate schema4, Catalog kind1/wrapper2, bundles39–44 and all existing normal1/2/experimental3 versions unchanged as design. To require conflict-aware readers, specify **feature38 wrapper version2** for the combined candidate profile: retain all feature1 fields in order, then `{commit_time_version:1,conflict_state_version:1}`. A future closure-only schema4 reader supporting feature38/version1 must reject version2 both on open and per transaction; it cannot ignore new review records while continuing to write. Current schema1/2 readers already reject marker4, and experimental3 is not repurposed. This is a versioned format addendum, not a silent reinterpretation of feature1 or a new live schema. Actual migration/profile activation still needs item3's separate authorisation, verified backup/quiescence, atomic feature/catalog update and cold/stale-reader evidence.
