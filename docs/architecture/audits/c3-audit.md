## Scope and outcome

The audit screened the 62 materialized contracts registered before this report and reviewed C3-bearing requirement, architecture, domain, subsystem, implementation, security/recovery and owner clauses. [Corpus identities and headings](../evidence/c3-specification-corpus.json) preserve the as-read scope. Private source archives remain provenance, not active specifications. All 31 registered compound requirement seeds have explicit mappings or exclusions below; source clauses beyond those seeds are covered separately. No claim that 31 seeds exhaust all atomic requirements is made.

The current C3 view shows **five logical responsibility areas and 11 internal connections**, plus **all 14 specified Rust/C2 boundary relationships**. Frontend delivery, explicit keychain lifecycle and cryptography are expanded as three existing adapter details so both internal boundaries and C2 endpoints are accurate. It is a simplified V3 discussion model, not a claim that five corresponding crates/modules already exist or an instruction to restructure the application. Existing model elements represent the broader areas through view-only titles and captions:

| C3 area | Detailed responsibilities retained in the model | Aggregate status |
| --- | --- | --- |
| Runtime and API | Startup/HTTPS/API; embedded frontend delivery | Implemented local slice |
| Application coordination | Command/publication coordination, authority, document/branch/composition workflows, graph/history reads, provenance, assertions, comments and protected clipboard | Partial |
| Pure domain | Dependency-free identities, exact-source validation and bounded planning | Partial |
| Workspace persistence | Record codecs/transactions, crypto, audit/recovery and explicit keychain lifecycle | Partial overall |
| Integration adapters | Agent, citation, import/export, GitHub-job and peer-exchange proposals | Planned |

The engine overview [component/source catalogue](../evidence/c3-components.json) retains its original **24 detailed responsibility elements**, including six nested planned adapters, and **56 source-linked logical flows**. Its `presentation` map assigns each responsibility to exactly one displayed area. Individual features are no longer all portrayed as independent C3 components. Most application and query code remains co-located in `crates/storage`; serialization stays at the adapter boundary and pure domain remains free of I/O.

Only principal internal dependencies are drawn; all Rust boundary connections to C2 neighbours are shown. Direct internal read/unlock routes, internal feature calls and future adapter policy/storage wiring remain in the model and catalogue; the simplified picture does not require every existing read to pass through the command coordinator. The engine remains one overview; the owner-requested [Runtime/API focused view](runtime-api-audit.md) is a separate drill-down. C1/C2 content, navigation and the saved C2 arrangement remain unchanged.

Block fills now carry no implemented/partial distinction: ordinary C3 components and neighbours use the same primary blue as C2; planned components use muted grey and dashed borders. Status badges are explicitly configured project-wide: **green = implemented within the model responsibility's stated bounded scope; amber = partial; grey = planned**. Previously the unconfigured badge palette assigned partial a green colour independently of the block fill. Broad area captions can include future responsibilities beyond an implemented representative's bounded scope; status assignment is unchanged. Group borders express hierarchy only. All architecture interpretation remains proposed; no product/format acceptance or new proof follows.

## Discrepancies and unresolved design questions

The original C3 view presented broad layers without the document, composition, query, evidence, policy and recovery responsibilities needed to inspect specification coverage. Those responsibilities are now visible and source-linked. The diagram still does not mandate a code refactor: authorization and publication/query functions are currently co-located in the storage adapter, and extracting modules is a separate design decision requiring a concrete benefit.

Retained source-era “not implemented”, “SQLite not selected” and explicit-Commit-only passages have historical scope; later accepted persistence/owner decisions and bounded evidence govern current claims. They are recorded, not silently rewritten. The external-witness proposal was expressly superseded by OWNER-009. Implementation is evidence, not retroactive acceptance of a new requirement.

Open mechanisms remain: general multi-owner/nested closure and Live resolution; production two-parent temporal records/origin composition/upgrade; general rights/delegation and historical keys; full provenance/interaction evidence; portable restore/repair and broad durability acceptance; exact provider/MCP protocols; Zotero credentials/origins; export/Pandoc packaging and profiles; encrypted GitHub job/remote reconciliation formats; independently trusted client delivery and core egress enforcement; federation convergence; local spellchecking allocation. No new code, persistence format, key custody, provider connection or runtime dependency is selected here.
