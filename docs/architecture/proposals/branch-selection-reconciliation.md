## Is an unnamed ordinary composition reachable?

**Not found in the inspected implemented lifecycle.** A new document gets an original branch; a named child belongs to that same document/node; its working state has an explicit branch context. Current ordinary editing therefore already has an owning branch. The owner's follow-up is expressly tentative (“Perhaps…”), so it is recorded as a source-backed hypothesis rather than final adoption of a universal lifecycle restriction.

The product's general constructed compositions and read-only projections are not implemented or fully specified. A comparison/query may draw exact sources from several branches without itself being a new branch. Conversely, one known owning branch of A can retain B@b1 in one snapshot and B@b2 in another. B's selected source branch/version does not become A's owner, and graph links do not prove which A branch owns a view. Thus an ordinary unnamed editable branch is **hypothetical, not a demonstrated necessary case**; general projection ownership remains explicitly unresolved.

Recommend the smallest lifecycle direction: keep normal editing in its existing initiating content-branch context, require explicit ownership/context before mutation, and treat a read-only constructed projection as a view until an authorised branch-preservation operation is designed. This is a recommendation, not permission to remove save-as-branch or a new requirement that every read-only query have a branch. OWNER048 still requires known origin/parent-or-position whenever a node is actually created, including creation by save-as if applicable.

## Newly directed behaviour and its boundaries

**Retained selections and indication (RQ040).** Reopening A restores its exact last-successful-acknowledged-autosave composition, including nested/repeated selections; it must not silently select a newer B or substitute the last Commit for the autosaved state. Routine autosaves must not accumulate historical versions merely because they occur. The future universal autosave/Commit relationship is reopened; earlier scoped workflow and immutable history/private visibility remain, with no new coalescing/deletion or publication mechanism adopted. A source-neutral indicator may report a newer version only within the viewer's authorised scope. It cannot disclose the existence, count or metadata of inaccessible versions. No refresh rewrites the retained state, inserts warning text into authored bytes or changes the exact source map. Historical reconstruction remains exact; current-authority queries for available updates are a separate projection. What “newer” compares—on a selected source track versus other authorised alternatives, including divergent versions—needs a concrete rule; no total ordering is inferred from graph linkage or timestamps.

**Preserve a constructed composition as a branch (RQ041).** Offer the owner-requested save-as-branch capability for an authorised constructed version of the current document when not already represented as a specific branch. Preserve its exact root, ordered structure, occurrence-specific selected versions, cycle context and source-affecting dependencies; retain the logical document/content identity instead of silently Forking. No constituent source identity/history is rewritten merely to name A's alternative composition. Current source authority, expected state, known creation origin and original-operation recovery still apply.

This capability does not require an originless or unnamed editable state: it can preserve a constructed selection from a known A branch context as an exact alternative. It must not be advertised as already implemented by ADR018's “create from this parent's current committed head.” General capture needs its own source-state, branch-parentage, draft/publication, completeness and compatibility design. If the same constructed state is already represented by a specific branch, selecting/retaining that identity and duplicate handling remain design work; byte equality or a name alone cannot merge branch identities.

**Main and caching.** A designated branch identity identifies which branch to reconstruct; exact retained selections determine that branch's composition under frozen policies. Main does not imply globally latest B/C/etc. A cache may later accelerate a deterministic reconstruction of the same exact branch/snapshot/profile; it is derived, discardable performance data, not authority for branch identity, selected versions or permissions. Cold construction and authorised cache hits would need byte/context equivalence, invalidation and resource evidence. This selects no algorithm, cache schema or persistence upgrade.

## Smallest remaining owner questions

These previously identified lifecycle dependencies are retained for traceability. The coordinator now presents remaining item1 decisions together; they are not new serial questions or implied adoption of adjacent branch/publication policy.

1. **Which meaningful events should retain a new immutable historical version, and may one such action also acknowledge an autosave?** The owner has settled last-autosave restoration and no routine history accumulation; universal operation separation remains open. [Input proposal revision7](trustworthy-reconstruction-inputs.md#revision7--approved-recovery-distinction-remaining-choices-in-one-batch) records OWNER052's accepted logical ordinary-recovery versus immutable-reference distinction only. General durable-reference events, meaningful publication against explicit/departure Commit and release/deletion remain unresolved. This approval does not select branch capture/publication or universal Save/Commit coupling; remaining item1 decisions are presented together by the coordinator. This is not a question about whether saved means autosaved.
2. **When preserving A's current autosaved constructed composition as a named branch, should the new branch begin as unpublished working composition or as a published exact state?** Recommend an exact capture leaving the source branch untouched, with the target's publication state chosen explicitly before implementation. This is broader than ADR018's committed-parent-head subset; it adopts no checkpoint/branch codec.
3. **Must main always be the initial/original branch, or may an authorised user explicitly designate a different existing branch as main?** Recommend a stable explicit designation, initially the original branch, with reassignment considered separately. Either answer reconstructs exact retained selections; neither chooses latest of every node or makes a cache authoritative.

The indicator's comparison relation is a follow-on representation/behaviour design input: first propose a source-backed rule consistent with followed/pinned tracks, divergence and permissions, rather than ask the owner to approve an unspecified timestamp policy. The earlier structural-position/source-projection relation, capacity, general permission/revocation, branch ancestry/publication and compatibility mechanisms remain open. No new decision is needed to reaccept retained history, known creation origin or the already requested capabilities.
