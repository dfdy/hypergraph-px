## Canonical state versus derived indexes

Canonical state includes immutable content/manifests/snapshots/events, exact retained working/recovery dependencies, private drafts, current heads, operation receipts, user/credential/policy/key catalogue, designated-main state, interaction/rights/citation evidence and original import mappings. A useful query index is not automatically canonical: any index declared derived must have a total deterministic rebuild from validated canonical inputs under the exact supported profile. If that relation cannot be established, classify the state as canonical and preserve it. Missing canonical evidence cannot be repaired by a current head, hash guess, provider fetch or empty record.

`Audit` freezes source schema/catalogue/policy and requested record families, authenticates records under independent expected contexts, verifies references/closure/ancestry and reports valid/incomplete/invalid with bounded protected findings. Continue only within the declared scope; no missing/denied/unsupported family yields an all-workspace-valid label. Audit is read-only and never writes an apparently repaired source.

`PrepareRepair` copies the frozen source consistently into a new private path and records expected source fingerprint/generation and original operation identity. Rebuild only declared derived families in deterministic ID/order using supported validated canonical data, bound source/input and generated bytes, and produce immutable report68. Source and original backup remain unchanged. `ActivateRepair` requires authorised explicit review of that exact report and unchanged expected source; perform an atomic path/activation switch after fsync/verification, retaining original and candidate copies. If the platform cannot guarantee atomic activation, report unsupported rather than overwrite. Crash/unknown outcome reconciles recorded intent/path fingerprints before any retry. Do not continue two active writers or delete either copy to hide ambiguity.

Repair/activation requires current edit+commit+read_history and explicit owner-reviewed administrative scope; index inspection never returns private source payload to an unauthorised caller. A complete encrypted recovery export additionally requires export and both administration capabilities plus an explicit local owner-controlled recovery-export approval freezing the entire protected namespace. It is not inferred from read_history, an unlocked key or ordinary admin rights, and is not an ordinary query of another user's draft. Partial authorised content export never silently expands into that recovery scope. Receiving/activation creates new local authority through the explicit bootstrap ceremony.

## Package v1 design

The portable container is a single binary stream, header `HPXP`, version u32 little-endian1, header-length u32, canonical UTF8 JSON header, then explicitly length-prefixed encrypted parts. Header fields in order are `{package:Id32,source_namespace:Workspace16,wrap:Bytes,manifest:Bytes,parts:L32}`. `wrap` is the exact existing HGWK representation wrapping an independently generated package data key against the expected source namespace/epoch1; it is not an authentication password or workspace grant. `manifest` is an HGOB ciphertext under that package key with authenticated package-manifest role/context. No new cipher or unreviewed streaming construction is introduced. Passphrase wrapping and per-object size guards remain the existing supported crypto profile; the package key and plaintext stay inside managed trusted adapter memory.

Decrypted manifest fields are `{package,source_namespace,profile:1,source_schema,source_catalogue:RecordRef,scope:exact frozen selection,interpretation_refs:[RecordRef],objects:[{ordinal:L32,role:name,logical_ref:RecordRef,slice_start:U53,total_length:U53,length:U53,sha256:Bytes}],keys:[wrapped key refs],resources:[exact object refs],terminal_parts:L32}`. Manifest/root and outer-part encryption use existing `Purpose::Index` with binding SHA256 of the fixed ASCII `HPX-package-v1`, package32, one-byte role (0=manifest,1=part) and ordinal u32 little-endian (0 for manifest); expected namespace/package/role/ordinal come from the frozen approved import/export intent, not trusting envelope fields. This adds no envelope suite/version or Purpose tag. A part plaintext may be an exact slice of an original encrypted record/resource; slices reassemble that original byte stream before its independent context authentication. Each appended part encodes ordinal u32 little-endian, byte-length u64 little-endian and one complete encrypted HGOB object. Validate U53/format/resource bounds before allocation, exact ordered ordinals/counts/lengths and SHA256 of each encrypted part against the authenticated manifest. Duplicate, missing, extra, truncated, reordered or altered parts reject. Hashes are ciphertext integrity lookup values, not public plaintext commitments or permission. The AEAD-verified manifest and expected context bind roles, package, part index and exact selected object; untrusted headers cannot supply their own expected authority.

Each part plaintext is at most16MiB, with smaller measured operational limits permitted. A larger logical byte resource uses explicit ordered slices in the authenticated manifest, each binding exact source identity, byte start/length and part ordinal; successful reassembly must cover the declared exact bytes without gaps/overlap. The manifest itself is one bounded object; if its validated representation exceeds supported limits, fail explicitly rather than invent an unbounded manifest tree. Aggregate input/output/temp/storage/work costs are admitted before each phase under OWNER054. No safe numeric platform capacity is asserted by these format ceilings.

Protected source objects retain their original authenticated bytes/contexts; any data-key material needed for exact historical reconstruction is wrapped under the package key using the managed adapter key-wrapping operation, never sent raw to a browser. Package creation must have authority for every selected historical key/dependency. Do not include hidden/private inputs merely because the workspace is unlocked. Exporting ciphertext still requires an explicit allowed backup/exchange scope; it is not a bypass for non-trusted plaintext-export denial.

## Restore and cross-workspace identity

Restore validates framing, wrapper/manifest AEAD, counts/lengths, every included supported record/interpretation/key/reference and complete declared scope into an isolated new workspace. It preserves the original file/package and never reuses the source's active writer. A forensic same-identity recovery copy is explicitly labelled as that same workspace and cannot be concurrently activated with its original; it is not enrolment into another workspace.

Cross-workspace import creates a new workspace identity and new local users/credentials/permissions. Keep the source namespace and immutable foreign record bytes as exact retained evidence, with explicit ExchangeMapping71 from `(source_namespace,kind,id,generation,version)` to local imported references. Importing does not authenticate foreign labels as local users. Newly allocated local graph references retain exact foreign source identity and derivation; original foreign history is not relabelled as a local user's authorship. Repeated import resolves the same validated foreign binding idempotently; conflicting bytes for the same purported foreign immutable identity reject. Same-node ancestry remains within its actual logical source identity, never fabricated as a cross-identity parent link.

The original foreign canonical records are retained as a protected read-only namespace with the exact source profile/keys needed for reconstruction. Local views resolve via the explicit mapping; they do not rewrite those originals, refresh heads or reuse source policy as local authority. Unsupported foreign profile/history remains preserved but unavailable, not silently converted into complete local content. Local edits create local authorised history with explicit foreign origin. Activation requires complete expected-scope validation and an original receipt; partial import remains a reported failed/staged candidate, not an active complete workspace. No existing manual workspace is recreated, enrolled or redirected by this design.

## Create-only GitHub backup

Freeze an exact verified encrypted package, target account/repository/ref/path, visibility, expected absence and its ciphertext fingerprint/length in private job67. Opening a dialog or connecting an account writes nothing. Explicit external approval names this precise target/package; permission and custody/egress policy are revalidated before upload and result release. Provider credentials are neither chat content nor graph authority.

Use GitHub's create-file Contents operation with the reviewed branch/path and **no existing-file SHA**. If the provider sees an existing path, fail rather than update it; a preflight GET alone is never the atomic precondition. The adapter pins the provider API profile and tests conflict semantics before capability enablement. Collision requires a newly reviewed name/intent, never an automatic suffix. Serialise conflicting local jobs and do not run update/delete against that target. Unknown timeout transitions to `uncertain`; query the exact original path/ref and compare verified bytes/fingerprint before deciding success, safe original retry or conflict. A mismatch never authorises overwrite. After verified create, persist provider commit/object identity in the original receipt and independently verify download/decrypt/manifest reconstruction before labelling restorable.

The [official Contents contract](https://docs.github.com/en/rest/repos/contents?apiVersion=2022-11-28) distinguishes creation from update, whose existing SHA is required. This design pins API2022-11-28 until an explicitly tested compatible refinement; documentation examples for newer versions do not silently change that pin. Provider size/rate/token limits are inputs to admission; oversized packages fail without issuing a partial backup, splitting into unreviewed names or declaring recovery complete. Restore always follows validated restore-as-new, never executes content from a repository. No GitHub tool write, connection, comment or issue is authorised by this specification.

## Explicit federation exchange

The initial D20A protocol is owner-reviewed authenticated package exchange, not continuous replication or a wall-clock conflict rule. The export/import approval freezes exact sending/receiving workspaces, counterpart/channel identity, scope, retained context and authority mappings. Secure transfer authenticates the chosen counterpart/channel or independently verified package key material; merely possessing a provider label or an untrusted self-declared namespace proves no authorship or authority. Preserve that evidence and its verification limit with the import receipt.

Validate the complete selected package, resolve explicit foreign references and obtain receiving-user authority before activation. Divergent imported developments remain branches with preserved histories until an authorised exact integration. Revocation stops future authorised exchange but cannot recall copies/keys already delivered. Partition/rejoin is repeated explicit package exchange and original-package reconciliation; no exactly-once remote delivery, causal convergence, CRDT or membership-crypto guarantee follows. Continuous peer replication remains a separately gated future expansion under D20A, not a missing mechanism claimed implemented here.

## Unexecuted acceptance

Test missing canonical data, denied audit scope, forged/derived-index authority, isolated repair crashes/activation races, malformed/future/huge/reordered/extra package parts, wrong key/context, exact multi-chunk byte reconstruction, restore namespace/identity and no carried permissions, idempotent/conflicting foreign imports, backup name races, provider rejection and unknown upload completion. Use genuine old readers and current custody/authority checks. No portable format, remote backup, repair or federated import has passed product acceptance by writing this contract.
