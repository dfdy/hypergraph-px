## Local authentication and session state

Workspace unlock loads storage keys; it never logs in a user. Before unlock, protected authentication records are unavailable and protected user authentication reports `locked`. The existing owner-controlled local launch admission permits only the explicit unlock/bootstrap ceremony, not graph access. No first-login administrator, OS-login authority or implicit legacy-user migration is allowed.

Human enrolment creates a distinct authentication password, not the workspace passphrase. Store a16-byte OS-random salt and32-byte Argon2id v19 verifier using the existing supported64MiB/3-pass/1-lane profile, bounded raw password1–1024 bytes without normalization. Authentication compares verifiers in constant time; no plaintext password persists. Machine enrolment creates an opaque credential ID and32-byte OS-random secret shown only at explicit enrolment. Its verifier is SHA256 over `HPX-machine-auth-v1`, workspace16, credential32 and the32-byte secret, with fixed-width components. Random machine secrets are not human passwords. Both credential forms are encrypted kind56 records and authenticate only their bound active workspace-local user. Auth credentials, storage keys and provider API keys are distinct; HPX owns no inference-provider account.

Serialize KDF work per workspace and apply bounded process-wide admission before allocation; queue exhaustion fails without starting KDF work. Rate-limit failures without exposing user existence; unknown, suspended, revoked and wrong-secret attempts have the same public authentication failure. Logs contain neither submitted material nor private identity existence. Enrolment/rotation/revocation are explicit authorised operations; rotation does not reuse a human password as a machine secret.

Successful authentication creates a fresh32-byte random in-memory session token bound to workspace/user/credential generation. Browser cookies are Secure/HttpOnly/SameSite=Strict, scoped to the validated origin with CSRF/Host/Origin enforcement. Session token digests, not raw tokens, are retained in server state. MCP credentials establish the same actor context through its protected adapter. Logout, lock, process exit, suspension or credential revocation invalidates dependent sessions; tokens never migrate across workspaces. Idle30minutes or absolute8hours expires a session; unsaved UI state is preserved explicitly but expiration cannot fabricate an acknowledgement. These are security lifetimes, not measured performance budgets. Every protected operation independently checks current lifecycle/policy, so a still-live token is not a frozen permission grant.

## Bootstrap, recovery and administration

Workspace creation is an explicit local ceremony, after storage-key creation/unlock and a validated private launch/control channel. It creates the initial human user, credential, full capability/assignment ceiling, policy generation0 and original receipt atomically. Generate a separate32-byte authentication-recovery secret, show it once for user-held storage, and retain only a domain-separated salted verifier in encrypted kind59. Recovery evidence is independent of both login and storage passphrase. Losing data keys still prevents decryption; authentication recovery cannot reconstruct them.

Recovery requires the explicit local owner-controlled ceremony, unlocked storage and the matching current recovery secret, never an arbitrary remote request. Freeze expected recovery/policy generation; consume/replace the secret, enrol the replacement administrator credential, invalidate prior sessions and append the recovery/policy/receipt history atomically. A lost acknowledgement retries the original operation; it does not show the secret a second time or repeat recovery. The user must verify safe retention before finalising the ceremony. No secret is placed in source, chat, logs or the manual workspace by tests.

`administer_users` changes another user's lifecycle; `administer_permissions` changes another user's explicit capabilities/ceiling. The actor must hold the relevant capability and every assigned capability/ceiling entry must be inside the actor's current ceiling. Administration cannot target oneself for increased authority. A non-escalating self-reduction is permitted only if it preserves a recoverable active administrator; self-suspension cannot strand the final administrator. An administrator is recoverable when an active human retains both administration capabilities, their matching ceiling and valid enrolled authentication/recovery evidence. Recovery is the explicit exception for restoring a lost final administrator, not a routine self-grant. Suspension never erases identity, attribution, receipts or history; a suspended machine user still occupies its provider slot. Reactivation reuses that user rather than adding another for the provider.

## Authenticated policy, concurrency and keys

Canonical policy57 and retained policy73 bind workspace, exact generation, user capability/ceiling/history-epoch sets and administration receipt. Every change validates expected generation, lifecycle, assignment ceiling and final-administrator invariant in the same transaction, updates current UserHead75 when lifecycle changes, inserts immutable change58/retained policy73 and receipt, and advances current57. Generation exhaustion fails. No symmetric authentication claim implies a signature or independent witness: AEAD authenticates policy within the trusted-server threat model; complete authentic workspace rollback remains undetectable under OWNER009.

Application admission checks current actor/policy before protected loading. Revalidate under publication serialization immediately before mutation commit, and immediately before protected query/receipt release. A concurrent policy change either precedes admission/release and is enforced, or follows the already completed release; there is no claim to recall delivered bytes. A revoked old operation may have completed, but replay cannot release its protected payload. Return an indistinguishable denied outcome until current authority permits reconciliation; never invent a second mutation because the receipt is now hidden.

Trusted-server key mediation retains independent storage-key and policy checks. `read_history` is not possession of missing historical epoch keys. The protected canonical key catalogue binds workspace, epoch, supported suite, wrapped-key reference and current/retained status. Each data epoch uses an independently generated32-byte key; key wrapping uses the existing XChaCha20-Poly1305 primitive with authenticated workspace/key-role/epoch context. A parent wrapping a child key is a new adapter operation over managed zeroizing buffers, not raw key export or domain serialization. Rotation creates the new epoch and catalogue transition atomically while preserving authorised old-key access; passphrase rewrap alone is not data-key rotation or revocation. Original encrypted objects and immutable refs remain; no bulk in-place re-encryption or history deletion is implied. Old copied keys/wrappers/plaintext cannot be withdrawn. Policy/history grants are enforced by the trusted server; this design does not claim malicious-unlocked-host confidentiality.

## Transport and client-held boundary

Local live delivery requires a valid trusted certificate for the exact loopback address/origin and private transport-key access. Provisioning creates key/certificate material in a private location, verifies SAN/chain/validity and key correspondence, shows the exact trust scope, and requires separate explicit owner trust approval. A new certificate is staged and verified before replacing the active configuration. Restart locked with fresh launch/session state; existing workspace bytes and user/data keys are preserved. Expiry, hostname mismatch, removed trust, invalid chain or renewal failure prevents live startup/use without HTTP fallback or warning bypass. Trust removal is explicit and causes subsequent validation to fail. TLS renewal is independent of credential/data-key rotation and does not enrol keychain.

Future client-held activation requires an independently obtained, owner-verified native client release fingerprint, signed/platform-validated distribution where applicable, embedded local UI and no executable code loaded from the untrusted storage host. Initial updating is explicit verified replacement through that independent channel, not server-supplied auto-update. The trust assumption is the independent installer/fingerprint channel and endpoint integrity; a fingerprint fetched from the same hostile server proves nothing. Browser-only delivery retains its hostile-code-delivery exclusion.

Custody transition freezes exact source/policy/key state, creates a validated encrypted copy with client-only keys, checks all retained history/resources and recovery, and activates only after explicit authorised review. Failure keeps the original; no in-place implicit migration, server key upload or config-only downgrade. All client-controlled plaintext sinks—export, clipboard, print, provider/context, plugins/jobs/cache/logs/telemetry—pass core egress policy; future non-trusted mode denies them even with read keys or confirmation. Protected local viewing/editing and separately authorised ciphertext exchange are distinct. Client-held remains unavailable until actual delivery, key, transition and sink acceptance passes.

## Required unexecuted acceptance

Exercise two humans/two providers, duplicate-provider suspension/reactivation, bad credentials, locked login, separate login/unlock, stolen/revoked session, final-administrator races, ceiling violations, recovery lost replies, current/history key denial, policy changes between prepare/commit/release, exact original receipt recovery, expiry/trust removal/renewal and malicious client-code delivery. Verify no plaintext secret or protected identity leak in logs/errors. Check current/older schema and crash/rotation recovery separately. No such application check is executed by writing this contract.
